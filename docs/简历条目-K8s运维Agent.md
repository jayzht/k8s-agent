## 项目经历

**K8s 智能运维 Agent** ｜ AI 应用开发 ｜ 2026.09 - 2026.10

**项目简介**：面向 Kubernetes 运维场景的对话式 Agent，基于 Tool Calling 构建
「自动取证 → 根因诊断 → 可批准处置」的任务闭环。重点设计**结构性读写分离的
安全执行架构**、提示注入防御、症状签名记忆、可插拔工具生态与确定性评测体系，
解决"Agent 真的能改生产集群"这件事在可控性、可审计性与可回滚性上的核心问题。

**技术栈**：Python、Tool Calling、Agent、Kubernetes API、MCP、Prompt Injection
Defense、评测工程

**技术亮点**：

- **结构性读写分离的安全执行架构**：把「看东西不用问，动东西要问」做进**代码路径**
  而不是提示词里——只读工具自动执行（取证不打断人）；写工具必须匹配一个已批准的
  `proposal_id` 才能执行，未登记工具一律 fail-closed 按写操作处理。提案卡片带影响面、
  服务端 dry-run、回滚方式与有效期，且**执行前重跑 dry-run** 关闭"批准到执行"之间的
  TOCTOU 窗口。危险动作分三档，最高档要求**手输目标名字**才能解开批准按钮——用摩擦
  而不是红色横幅对抗告警脱敏。

- **提示注入防御与参数化工具边界**：集群数据（Pod 日志、事件、ConfigMap）全部用
  `<untrusted>` 围栏标注并做加权评分扫描，且**只标注、绝不删改原文**（删改会毁掉
  运维赖以判断的证据）。所有写能力都是参数化工具、可改字段枚举化，**不提供"应用任意
  YAML"的入口**，从根上消除注入载荷的执行面；抗注入作为**独立指标**统计，不混进总通过率。

- **症状签名记忆与经验沉淀闭环**：用确定性 token 计算症状签名、以相似度检索结构化案例库
  （**刻意不用向量 RAG**：小样本下要的是可解释与"宁可不给建议也不给不相干经验"），
  且只有回查确认**症状真的消失**的处置才允许沉淀。实测发现单独立一个检索工具
  **15 个场景调用 0 次** → 改为把命中的经验**自动附带**在模型本来就会调用的工具输出里，
  命中率才真正上来；并通过增加区分性 token 解决"两类故障症状签名撞车、导致相反处置
  互相污染"的问题。

- **上下文工程与协议级不变量**：历史按"轮次单元"裁剪，**绝不切断 assistant(tool_calls)
  与 tool 结果的配对**；退化循环护栏（同参数重复 / 连续落空）同样**延后到本回合结果
  落完再注入**。两者都踩过真实的 400 错误——协议不变量被破坏时，表现为"整个会话突然崩掉"
  且看起来像模型服务故障。据此把长会话稳定性与 token 成本做成可预期、可回归的工程属性。

- **可插拔工具生态与双向 MCP**：设计 Provider 接入层，让可观测性数据源、发布历史、
  外部 MCP Server 以只读方式挂载；**写工具必须自带 dry-run 与 apply 实现才允许注册**，
  把"扩展能力"和"不削弱安全边界"绑定在一起。MCP 双向打通（既能作为 server 暴露只读工具，
  也能作为 client 接入外部工具，默认拒绝 + 显式白名单），使工具面可以外部扩展而无需改核心。

- **确定性评测体系与工具演进闭环**：自建 16 个故障剧本 + **确定性判据（不用 LLM 当评委）**，
  支持不重跑模型的重新判定。评测暴露出一条反直觉结论：**加新工具会改变模型在别的场景里的
  行为**——新增回滚工具后模型主动换用了它，6 个场景从旧工具切到新工具。因此把评测判据
  从"只看调用哪个工具"升级到"**校验工具参数**"（例如回滚版本号必须是真的可回滚目标，
  指到当前版本等于空操作），并确立"每次加工具必须重跑全量评测"的工程纪律。

## ⚠️ 面试时不要说的（比上面每一条都重要）

| 别说 | 为什么 |
|---|---|
| "生产级" / "线上验证过" | 单集群 kind 沙箱、合成演示应用、**零真实用户**。一问就穿 |
| "诊断准确率 100%" | 最近一次全量单跑 16/16，但**历史区间是 12~15/15**，且**新题库只跑过一次**。单次满分不是稳态 |
| "16 个真实故障" | 是**我自建的剧本**（自己写的故障注入 + 自己定的期望值）。这是这个项目**最弱的一环**，要主动交代 |
| "覆盖运维 80% 的工作" | 覆盖的是「症状 → 一个可批准的方案」这一段**工作流**，不覆盖发现、排班、沟通、变更流程、集群生命周期 |
| "多集群 / 高可用" | 只有单集群；角色只有 operator / viewer |
| "用了 RAG" | 记忆**故意用确定性签名检索而非向量 RAG**。硬说 RAG 会被追问"为什么不用向量"，而正确答案是"小样本 + 要可解释 + 不能让不相干经验被照抄"，这反而是加分项 |
| "所有危险动作都能解锁" | 默认拒绝 8 个里只有 1 个可显式解锁，3 个永久禁止，4 个还没实现 |

**最强的说法**（建议背下来）：

> 这个项目最值钱的不是诊断率，是**安全执行架构**：只读自动跑、写操作在代码路径上
> 拦住、未登记工具 fail-closed、提示注入有防线且检测到必须告知人、危险动作靠手输确认
> 制造摩擦。而且**我清楚它会在哪儿失效**——16 个剧本是我自己出的题，
> 单集群合成应用，没有真实用户。这两句放在一起，比任何一个通过率数字都更能说明工程判断力。

## 与其他项目的位置关系

- 和你简历里的 **RAG 项目**互补：那一个是"检索质量"链路，这一个把**"Agent 真的动手"
  的信任链路**做完了。投 Agent 岗时这一条的分量更重，因为**大部分同岗位候选人只有
  "能调用工具"，没有"敢让它调用工具"**。
- 和你简历里的 **MiniCode** 互补：MiniCode 是 Coding Agent（Skill 路由、上下文压缩、
  多 Agent 协作），本项目是 **Ops Agent**，共同点是都围绕 Tool Calling 与上下文治理，
  差异点是本项目把**权限与安全审查**做成了结构性约束而不是策略配置。
  > ⚠️ 如果面试官问"这两个项目的权限安全审查有什么区别"，要能答出实质差异：
  > MiniCode 侧是"规则过滤 + AI 风险分类 + 人工确认"；本项目是**代码路径上的强约束**
  > （写工具拿不到批准的 `proposal_id` 就执行不了），不依赖任何规则判断。
