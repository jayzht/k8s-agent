# 这个评测能证明什么、不能证明什么

> 这份文档不是在讲评测怎么用（那是 `docs/usage.md`），是在讲**它的可信度边界**。
>
> 写它的原因：这个项目的历史上，通过率被报过 15/15、14/15、16/16、21/22、25/25——
> 而**每一次"变好"背后，都查出了数字本身的问题**。一个不可信的评测比没有评测更糟，
> 因为它会让你以为自己做对了。这份文档就是把这个风险讲清楚。

---

## 一、一句话结论

> **它是一个"受控环境下的工程回归套件"，不是一个 benchmark。**
>
> 它能回答："我改了代码之后，行为有没有退化？"
> 它**不能**回答："这个 Agent 在真实运维里有多大用？"

---

## 二、它**已经证明**了的事（可信的部分）

这些结论不依赖通过率，是靠**逐条复核**得到的，我认为站得住：

1. **它能发现真实 bug。** 评测跑出来的失败里，有一批最后定位到的是产品代码的缺陷，不是模型问题：
   - 退化循环护栏把 `system` 插进 `assistant(tool_calls)` 和它的 `tool` 结果之间 → API 稳定 400，
     **伪装成"模型不行"**
   - 同一条 `tool_call` 被两条修复路径各补了一次结果 → 会话永久 400
   - 会话回收按 `created_at`（创建时间）算 → **把正在跑的排查踢出内存**，
     用户看到的是"服务一直在重启"
   - `target_of()` 用 if 链 + 兜底 → 4 个写工具的确认卡片**显示错目标**，其中两个名字是空的
2. **"加工具 ≠ 模型会用"。** 单独给模型一个"查最近变更"的工具，**15 个场景调用 0 次**；
   改成把信息**内联进模型本来就会调的工具**才生效。
3. **"加工具会改变模型在别的场景里的行为"。** 新增回滚工具后，模型在 **6 个旧场景**里
   主动换用了新工具——评测没跟上，一次跑出 9/16。**那不是回归，是预期没跟上。**
4. **它能在别人造的应用上工作，但取决于信号。** 拿 Google Online Boutique 做对照：
   Chaos Mesh 的故障答对了（靠 Chaos 自己写进 Events 的"自白书"）；
   **把同样的延迟静默注入（无 CR、无事件）后答错了**——把一个下游的网络延迟误判成
   调用方的 CPU 限流，而它自己读到 CPU 只有 17m / 200m 限额、限流物理上不可能。
   归因是**缺信号，不是缺工具**（18 次调用，该读的都读了）。

## 三、它**不能**证明的事（不可信的部分）

### 3.1 通过率不是能力指标

历史上报过的每一个数字，查下去都有问题：

| 报出来的 | 查出来的问题 |
|---|---|
| 15/15 | 单次采样，不是稳态（同一套题库 run13 又掉回 14/15） |
| 16/16 | 题库是旧的，改了 `hpa` 的预期之后没重跑 |
| 21/22 | 题干泄题 + 数据源没接 |
| 25/25 | **至少 2 个 pass 是空心的**（见下） |

### 3.2 "不动手就算过"这个漏洞

`expect=∅` + `allow_none=True` 的场景，判定上**只要求"没提出写动作"**，
而 `mentions`（结论里该出现的关键词）在历史设计里**只是参考指标、不计入 passed**。

后果：**分不出"诊断对了所以不动手"和"诊断错了但也没动手"。**

真实案例（`stress` 剧本，CPU 被外部压力实验打满）：

| 配置 | 它提出 | 判定 | 它有没有提到 StressChaos |
|---|---|---|---|
| 有泄题的题干 | `patch_resources`（错） | **FAIL** | — |
| 去掉泄题的题干 | 不提任何变更 | **PASS** | **没有**，说"集群正常" |
| 再去掉泄题 + 接上指标 | 不提任何变更 | **PASS** | **没有**，错判成"探针端口 + HPA" |

**去掉泄题没有让它挂，只是把失败模式从"提错动作"变成了"根因错但不动手"——
诊断更差，分数更好。**

### 3.3 评测会用**自己制造的垃圾数据**当证据

每跑一个场景，评测都会注入故障再恢复。K8s 对象和 Chaos 对象都 reset 了，
**但 Loki / Prometheus 的历史没人清**。

于是 `noissue`（考"集群健康时不许编造故障"）在接上指标之后，
把**评测自己前面场景留下的 churn**（534 条 `kube_pod_created`、`postgres-primary-0` 反复被 Kill）
当成了"命名空间在被反复重建"，**编造出了一个不存在的故障**——然后**照样通过**。

### 3.4 报告里的"查证"是残缺的

`evaluate_one` 统计 `read_calls` / `read_tools` 时用的是**静态表** `READONLY_TOOLS`（15 个内置工具），
**provider 工具（Prometheus / Loki / 变更历史）一个都没被记进去**。
那一次全量里真实跑了 **64 次** provider 调用，报告里记了 **0 次**。

所以"查证 100%"这个数字，只说明它调了内置工具。

### 3.5 题干会**泄露答案**

不点名元凶，很多剧本根本不可能过（因为 Agent 没有读 Chaos 对象的工具）。
已经改掉 3 条，但 `dependency` 这类"通用题干点名了 `expect` 要救的那个服务"的情况
可能还有——因为通用题干的形式就是「`<受影响工作负载>` 好像出问题了」，
而**"查哪个服务"本身就是任务的一部分**。

### 3.6 最根本的一条：**自己出题自己考**

剧本、故障注入、期望值、判分——**全是同一个人写的**。
Google Online Boutique 那次对照实验就是为了撞这个边界，结论是：
**在别人造的应用上，只有在"信号够"的时候它才诊断得对。**

---

## 四、所以对外该怎么说

**不要报通过率。** 要报的是这三句：

> 1. 我建了一套**确定性判据**的评测（不用 LLM 当评委），**16 → 25 个剧本**，
>    覆盖单故障、组合故障、注入、以及"正解是不动手"的克制类场景。
> 2. 它的价值不是那个百分比，是**它反复推翻了我自己的结论**——
>    我报过的每一个"变好"，最后都查出了数字本身的问题（泄题、空心通过、缺信号、统计口径残缺）。
> 3. 我拿一个**别人造的应用**（Online Boutique）做了对照，确认了瓶颈在**信号**而不是工具或模型能力。

**"我的评测在骗我，这是我怎么发现的"** —— 这句话在面试里的分量，
比任何一个通过率都重。因为它证明的是**工程判断力**，不是分数。

## 六、一条方法论

这个项目里反复出现同一个模式，值得单独记下来：

> **先量，再改。**
>
> 想做"区分度加权"之前，先把真实配对分数算出来（同一工具 1.00、不同工具 0.57、中间是空的）
> → 才知道该取 0.7 还是该改算法。
> 想加"区分 token"之前，先实测两个场景的签名
> → 才发现**两个场景都改了 pod 模板**，那个判据根本不成立，于是**没有 ship**。
> 想报"25/25 变好了"之前，先逐条复核 pass 的构成
> → 才发现至少 2 个是空心的。

**没量就改，等于用一个你没验证过的判据去替换另一个。**
