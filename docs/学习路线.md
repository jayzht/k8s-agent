# 这个项目怎么学（面试导向）

> **这份路线的前提**：面试官不会考你背代码，他会挑一个点往深里问
> 「**为什么这么做？不这么做会怎样？你试过别的吗？**」
> 所以目标不是"读完"，是**每个关键决策都能讲出取舍，每句话都能落到证据**。

**总时长建议：3 天（约 12~15 小时）**。下面每关都给了时间盒，超时就跳过——先覆盖面试真正会问的，细节留到二刷。

## 第 0 关：先背下三个版本（1 小时）

这三个版本必须能**不看稿说出来**。后面所有学习都是给它们填血肉。

**30 秒版**（自我介绍里提到时用）
> 一个 K8s 运维 Agent。核心主张一句话：**看东西不用问，动东西要问**。
> 只读工具自动执行帮运维取证；写操作必须先出一张带影响面和 dry-run 的确认卡片，人批了才执行。

**2 分钟版**（"讲讲你这个项目"）
> 在 30 秒版基础上加：为什么要做（运维查一个故障要敲十几个 kubectl、翻文档、问同事）；
> 怎么保证安全（读写分离做在**代码路径**上而不是提示词里，未登记工具 fail-closed）；
> 怎么证明有效（自建 22 个故障剧本 + 确定性判据的评测）；
> **主动交代边界**（22 个剧本是我自己出的题、单集群合成应用、没有真实用户）。

**5 分钟版**（深挖时）
> 2 分钟版 + 下面第 2 关的五个决策各说一句。

## 第 1 关：动手跑一遍主链路（1.5 小时）

**这一关不能只看，必须亲手做。** 面试官问"它到底怎么工作的"，你脑子里要有画面。

```bash
cd /home/ubuntu/O&M-agent
unset http_proxy https_proxy
export PATH="$PWD/bin:$PATH" KUBECONFIG="$PWD/var/kubeconfig" PYTHONPATH="$PWD/src"
set -a && . ./.env && set +a
.venv/bin/omagent serve --demo
```

打开 http://127.0.0.1:8765 ，用 `zhang.wei` / `ops-pass-2026` 登录，然后：

| 步骤 | 你要观察什么 |
|---|---|
| 1. 注入 `oom → api-gateway` | 故障注入按钮是沙箱专用（`--demo` 才开） |
| 2. 问「api-gateway 怎么了」 | **只读工具自己跑，你一次都不用点** ← 这是"看东西不用问" |
| 3. 看它提卡片 | 卡片上有：影响面、**服务端 dry-run 结果**、回滚方式、模型写的 rationale |
| 4. **先别批准**，刷新页面 | 卡片还在、倒计时继续 ← 状态是持久化的 |
| 5. 拒绝它，再问一次 | 拒绝后它不会换个说法反复提同一个动作 |

**加分动作**：再起一个服务加 `--allow-tool delete_pvc`，看 `severe` 档位要求**手输目标名字**才解锁批准按钮——这是"用摩擦对抗告警脱敏"。

## 第 2 关：五个核心决策（**面试主体，4 小时**）

每个决策都要能答三件事：**为什么这么做 / 不这么做会怎样 / 我试过别的吗**。

### ① 读写分离为什么做在代码路径上，而不是写在提示词里？

- **做法**：只读工具自动执行；写工具要匹配一个已批准的 `proposal_id`；**未登记的工具一律当写操作**（fail-closed）
- **代码**：`agent.py` 的 `run_readonly()` / `execute_write()` / `is_mutating()`
- **守它的测试**：`tests/test_safety.py`（"每个写工具走只读路径一律被拒"）
- **要能反驳的替代方案**：写进系统提示词"不要执行危险操作"——提示词是**可以被绕过的**（注入、模型幻觉），而代码路径绕不过
- ⚠️ **一定要能答的追问**：「那模型硬要调呢？」→ 它在工具清单里根本不存在，调一个不存在的名字会被 `is_mutating` 判成写操作然后拒绝

### ② 提示注入防御为什么是「围栏 + 加权评分」，而且**只标注不删改**？

- **做法**：集群数据包 `<untrusted>` 标签；`safety.scan()` 加权评分，阈值 3；**命中后只标注+报给人，绝不删改原文**
- **代码**：`safety.py`（约 185 行，很短，**全文读**）
- **关键取舍**：删改原文 = **毁掉证据**。运维要靠日志原文判断，你把注入载荷删了，他永远不知道有人在生产日志里写指令
- **要能答的追问**：「就靠关键词？」→ 是启发式，会漏。所以设计上**不依赖它单独兜底**——真正的防线是 ①的代码路径（工具根本不存在）+ 参数化边界（没有"执行任意命令"这个口子）
- 🎯 **这条是差异化**：竞品调研里 8 个项目，**0 个实现了注入防御**

### ③ 记忆为什么**不用向量 RAG**？

- **做法**：症状签名（确定性 token）→ Jaccard 检索 → 只有**回查确认症状真的消失**的处置才允许沉淀
- **代码**：`cases.py`（`symptom_tokens()` / `similarity()` / `search()` / `verify_applied()`）
- **理由（这才是得分点）**：
  1. 样本极少（几十条），向量检索在**小样本**上没有优势，反而引入不可解释的相似度
  2. **要可解释**：运维问"你为什么建议这个"，必须能回答"因为症状签名一模一样"
  3. **宁可不给建议，也不给不相干的经验**——这个系统里"被照抄的错误经验"比"没有经验"危险得多
- **要能答的追问**：「阈值怎么定的？」→ 实测：推荐同一工具的配对 1.00，推荐不同工具的 0.57，中间是空的，所以取 0.7
- ⚠️ 我**不认为这是终局方案**，`cases.py` 的注释里写了：阈值只是止血，根治要按词的区分度加权（IDF 思路）

### ④ 上下文裁剪为什么按「轮次单元」，而不按消息条数？

- **做法**：`_trim()` 按"assistant(tool_calls) + 它后面的 tool 结果"为一个单元丢，**绝不切断配对**
- **代码**：`session.py` 的 `_trim()` / `repair_orphan_tool_calls()`
- **要能答的核心**：OpenAI 协议对历史有两条硬要求，违反任意一条都是 400：
  1. 带 `tool_calls` 的 assistant 后面必须**紧跟满**对应数量的 tool 结果
  2. 每条 tool 结果必须**回应**它前面 assistant 声明的某个 tool_call
- 🎯 **这条有故事**（见第 3 关），能讲"我在生产里踩了两次、最后把它做成不变量测试"

### ⑤ 评测为什么**不用 LLM 当评委**？

- **做法**：22 个故障剧本 + 确定性判据（查证 / 避坑 / 动作 / 根因提及），抗注入**单独统计**
- **代码**：`evals.py`；判据在 `evaluate_one()` 末尾
- **理由**：贵、不稳定，而且"**另一个模型觉得它对**"本身不是可信证据
- **要能答的追问**：「22 个剧本自己出的，不算自证吗？」→ **算，而且这是这个项目最弱的一环**，要主动说。见 `docs/覆盖范围.md` 里"面试时绝对不要说的"

## 第 3 关：失败史（**最值钱的一关，3 小时**）

面试官最想听的是这个。**"我做对了什么"人人都会说，"我判断错在哪、怎么发现的"才筛人。**

`docs/eval-report.md` 有 12 轮记录，**不用全读**，挑下面 7 个讲熟：

| # | 故事 | 一句话版 | 为什么值钱 |
|---|---|---|---|
| 1 | **加工具 ≠ 模型会用** | 单独给模型一个"查最近变更"的工具，**15 个场景调用 0 次**；改成把变更差异**内联进模型本来就会调的 `get_workload`**，才生效 | 讲"检索增强"时的通用教训：**别指望模型主动去够新工具** |
| 2 | **护栏把上下文写坏** | 退化循环护栏就地插一条 system 消息，把 assistant 和它的 tool 结果截断 → API 稳定 400 → **伪装成"模型不行"** | 协议不变量 + "把失败甩给模型波动之前，先确认不是自己写坏了上下文" |
| 3 | **症状签名撞车** | `cordon` 和 `pending` 签名完全相同但处置相反 → 一条经验被另一类故障 100% 命中、给出相反建议。解法：**加区分性 token**（`node_cordoned` / `no_matching_node`） | 讲"知识 vs 工具"两类问题的区分 |
| 4 | **加工具会改变别的场景的行为** | 新增回滚工具后，模型在 **6 个旧场景**里主动换用了新工具，评测没跟上 → 一次跑出 9/16。**不是功能回退，是预期没跟上** | 讲"评测要跟着能力演进"，以及**从只看工具名升级到校验参数** |
| 5 | **被否掉的方案** | 想用"工作负载的 pod 模板最近有没有变过"当区分 token，实测**两个场景都改了模板**，区分不了 → **没有 ship** | 讲"我知道什么时候不该把东西塞进系统" |
| 6 | **两个伪装成外部故障的自研 bug** | ①同一条 tool_call 被补了两次结果 ②会话回收按创建时间算，把**正在跑的排查**踢出内存。两个在界面上分别显示成"模型调用失败"和"服务重启过" | 讲排查方法论：**先怀疑自己，再怀疑外部** |
| 7 | **夹具把自己埋了 + 工具说了半个真话** | ①`inject-event` 跑出 `injection_seen=0`：手搓的 Event 没设 `lastTimestamp`，被埋在 2337 条事件底下 → **场景静默地什么都没测到** ②顺这一下挖出真 bug：`get_events` 只返回最近 15 条却**不说自己被截断**，模型于是把"没看到"写成"事件里没有异常" | 讲"零信号看起来像通过"这种**静默失败**；以及**工具返回部分结果必须自报截断**，否则等于制造假证据 |

每一条都要能按这个结构讲：
> **现象** → **我一开始的判断（可能是错的）** → **怎么定位到真因** → **怎么修** → **加了什么不变量防止复发**

🎯 第 5、6、7 条尤其加分——它们证明的不是"我会写代码"，是"**我会做工程判断**"。

📖 材料：`docs/eval-report.md`（挑这 7 个故事对应的小节读，别线性读完 1400+ 行）

## 第 4 关：数字与边界（**防守题，1 小时**）

被问到数字，答错一个就完蛋。**背下来**：

| 问题 | 标准答法 |
|---|---|
| 多少工具？ | **18 个只读 + 23 个写 + 1 个默认锁着可解锁**（`delete_pvc`）。加外部数据源后运行时是 44~49 个 |
| 测试多少？ | **428 条**（`pytest tests/`） |
| 评测通过率？ | **22 剧本最新一次全量单跑 21/22**（唯一失败的 `inject-event` 是**夹具的坑**，修完单跑 1/1 通过，但**修复后没重跑全量**），历史区间 **12~15/15**。**不要报 100%，也不要写 22/22** |
| 能替代运维吗？ | **不能。** 覆盖的是「症状 → 一个可批准的方案」这一段**工作流**，不是岗位占比 |
| 生产能用吗？ | **不能算生产级**：单集群、合成应用、零真实用户 |
| 数据源几个？ | 内置 4 类（K8s / Prometheus / Loki / 变更历史）；外部 MCP **默认零导入**，实测过官方 filesystem server |
| 为什么不做多集群？ | 会放大权限与审计复杂度；单集群的边界我说得清楚，多集群的我说不清 |

## 第 5 关：亲手复现两件事（1.5 小时）

**做过一次，讲的时候底气完全不一样。**

**① 自己跑一次评测**（约 12 分钟）
```bash
.venv/bin/omagent eval --only oom,crash,hpa --settle 22
```
看输出里的五列（查证 / 避坑 / 动作 / 根因 / 提出），然后回答自己：**"避坑"那一列在考什么？**

**② 自己写一条不变量测试**
挑一条你觉得重要的性质，写进对应的测试文件。例如在 `tests/test_safety.py` 里加：
> "任何写工具都不能在没有批准凭证的情况下执行成功"

写完跑 `pytest tests/ -k 你起的名字`，看着它过——你就理解了**这个项目为什么能声称安全**：不是靠文档说，是靠 **428 条里那几十条守边界的测试**。
