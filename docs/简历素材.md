### 版本 A：一行版（放在技能栏或项目列表）

### 版本 B：标准版（4 条，最常用）⭐ 推荐

> **K8s 运维 Agent** ｜ 个人项目 ｜ Python / Kubernetes API / LLM
>
> - 独立设计并实现面向 Kubernetes 的运维 Agent，覆盖**工作负载 / 服务网络 / 配置 / 依赖 / 节点集群 五层根因、19 类故障**，在本地 kind 集群完成端到端验证（非 mock）。
>
> - 针对「AI 触碰生产」的核心风险，设计并落地**三条结构性安全不变量**——工具级固定审批切分、方案生成与执行分离、审批凭证与方案强绑定；以 **25 条对抗测试**固定，覆盖伪造批准凭证 / 凭证调包 / 绕过门禁 / 审计篡改，**越权拦截率 100%**。
>
> - 从零搭建**评测体系**（68 条故障用例 + 离线回放 + CI 安全护栏 + 用大模型生成"规则之外"的对抗场景），并接入 **IBM ITBench 真实事故数据集**，取得首个非自证评测结果；**评测驱动修复 10+ 个真实缺陷，其中 2 个是自身引入的假阳性**。
>
> - 实现 Web 审批台与自然语言入口，前端**在结构上无法绕过安全内核**（仅持有方案 ID，动作对象存于服务端）；实测单次诊断成本约 **¥0.003**。

### 版本 C：技术详版（投后端/平台/AI 应用岗，可拆成两段）

> **K8s 运维 Agent** ｜ 个人项目 ｜ Python · Kubernetes API · LLM Agent ｜ 约 8900 行
>
> **背景与定位**
> 运维场景中 AI 落地的瓶颈不是"能不能诊断"，而是"**敢不敢让它碰生产**"。项目把自主权明确定在 **L1（只读诊断自动、写操作必须人工确认）**，并把产品重心放在"**让值班的人 30 秒内敢点确认**"。
>
> **安全设计（核心）**
> - 落地**三条结构性不变量**，且不依赖提示词约束：① 每个工具在代码里声明是否 mutating，启动时与策略文件交叉校验，不一致**拒绝启动**；② 方案生成与执行是两段代码，`propose()` 永不产生副作用；③ `execute()` 需要 `approved=True` 且 `proposal_id` **严格匹配**的凭证，批准 A 执行 B 会被拦下。
> - 动作按危险度分 **T0–T3 四档**，T3（删负载/命名空间/PVC、碰 Secret、改 RBAC）**直接拒绝，任何人批准都无效**；熔断规则（命名空间/节点白名单、保护标签、爆炸半径、变更冷却、冻结窗口）**全部配置化**，不写死在代码里。
> - 写操作强制**服务端 dry-run** 预校验，未通过不生成可执行方案；审计日志采用**哈希链 + 进程间文件锁**，可检出篡改与删除。
>
> **诊断能力**
> - 覆盖五层根因，并把**归因优先级固化为纪律**：配置 > 依赖 > 网络；集群级问题优先于工作负载级（否则会把"自己配错"判成"对方挂了"，或对一个注定失败的对象反复重启）。
> - 依赖层实现**三分归属**：端口冲突→我们配错 / 对方 0 就绪后端→**对方挂了** / 端口对且有后端→网络层。三种情况给出完全不同的处置与归属。
>
> **评测与效果**
> - 68 条故障用例（19 类签名），每条都标注"**绝对不能提的动作**"——把"没做错事"和"做对事"一起度量；把"危险动作提议数 = 0"做成 **CI 构建门禁**。
> - 用大模型生成"规则之外"的对抗场景反测规则引擎，**三轮 18 个场景挖出 **6 个假阳性 + 4 个漏报 + 2 个未识别****；其中一次直接证明**我自己写的一条既有用例的期望值是错的**（照搬了实现的错误行为）。
> - 接入 IBM ITBench-Lite 真实事故数据，**35 个场景中 3 个落在能力范围内，实测 3/3 命中**，且归因正确（结论指出的环境变量与端口与真实注入故障完全一致）。
>
> **关键取舍**
> - 对比两套规划器并**发现自己的评测工具有 3 个保真度 bug**（把 LLM 分数压低了一半）：
>   修复后 LLM 从 55.9% 升至 89.7%，但**重跑又掉到 54.4%——暴露 LLM 评测存在巨大方差**，
>   因此**不报单一数字**；而规则引擎的 100% 是确定性的、可复现的。
>   两套规划器的**安全指标完全相同且都是满分**（门禁用例 5/5、对抗用例 5/5、门禁泄漏 0），
>   说明**安全不依赖模型质量**。

## 附录：规划器对比——一个"我差点写进简历的假数字"

> 这一节比任何技术细节都值得讲。**它是我在准备简历时自己抓出来的。**

### 事情经过

我原本写的数字是「规则引擎 68/68、LLM 55.9%」。看着很有说服力——**但它是假的。**

排查后发现：**我的测试替身（FixtureK8s）有 3 个保真度 bug**，它们

| # | bug | 后果 |
|---|---|---|
| 1 | 假工作负载对象缺 `image` / `node_selector` 字段 | `get_workload` 工具**整条抛异常**；LLM 拿到"工具内部错误"，只能回答"证据不足" → **68 条里 33 条受影响** |
| 2 | `get_services` / `get_configmap` 登记进了工具白名单，**却漏接了只读分派器** | LLM 一调用就拿到 `ActionRejected` |
| 3 | `get_endpoints` **自己算了一遍**、忽略 fixture 的 `endpoints` 设置 | 规则引擎看到"端点为空"，LLM 看到"端点正常"——**同一概念两条代码路径，结论互相矛盾** |

**三个 bug 的共同点：替身不与真实接口同构。**
我测的不是产品，是替身。而 LLM 是唯一会去**调用工具**的规划器，
所以**所有替身缺陷都只打在它身上**。

### 修复后

| 阶段 | 严格通过 | 签名准确率 | 受工具错误影响 |
|---|---|---|---|
| run1 原始（替身有 bug） | 38/68 (55.9%) | 67.7% | **33/68 条** |
| run2 修 `image`/`node_selector` + 补分派器 | **61/68 (89.7%)** | **97.1%** | 0 |
| run3 再修端点一致性 | 37/68 (54.4%) | 70.6% | 0 |
| run4 **配置与 run3 完全相同** | 42/68 (61.8%) | 73.5% | 0 |

### 但真正重要的发现是最后两行

**run3 和 run4 的代码一模一样，跑出来 54.4% vs 61.8%——差 7.4 个百分点。**

排查确认**不是 bug 复现**：`investigation_turns` 从 28 涨到 61、
`abstain` 从 23 涨到 37——**模型查得更多、但更不敢下结论。**

也就是说：

> **LLM 规划器的评测有巨大方差。**
> 修完所有 bug 后，同一个 harness、同一套用例、`temperature=0`，
> 四次跑分落在 **54.4% – 89.7%** 区间。
> **单次跑分不能用来给 LLM 打分。**

（temperature=0 并不保证确定性——托管推理的连续批处理与 MoE 路由
都会带来输出漂移。而 agentic 多轮工具调用会**放大**这种漂移：
一次早期工具调用的差异会级联到后续所有轮次。）

### 那规则引擎的 68/68 呢？

**它是确定性的**——同样输入永远同样输出，跑十次还是 68/68。

所以这组对比真正说明的不是"规则比 LLM 准多少"，而是：

> **在要求可复现、可审计的运维场景里，
> 一个确定性规划器本身就是一项优势——因为它能被验证。**

### 剩下的失败里，LLM 真的错了吗

逐条看剩余失败，**大部分不是推理错误**：

| 类型 | 条数 | 说明 |
|---|---|---|
| 签名正确、但**拒绝提议动作** | ~9 | 理由多为"证据不足，不宜贸然重启"。**在运维语境下这是负责任的行为**，却被我的评分判为失败 |
| 结论实质正确、但**标签与我的命名不同** | ~3 | 如 dep-001：LLM 说"根因在工作负载之外，依赖 kafka 不可达，重启回滚都无效，建议转交依赖方"——**这在语义上就是 `dependency_unavailable`**，只是它标成了 `crashloop` |
| **我的期望值偏保守** | ~2 | 如 sched-002/003：LLM 说"根因是调度约束/污点，修复需要改 toleration 或节点，**不在当前动作清单覆盖范围内**"——**它是对的，我期望的 `scale_workload` 修不好这个问题** |
| **真正的推理失误** | ~2 | 主要是缺了"**把日志里的端口与 env 配置、Service 真实端口做交叉比对**"这一步 |

### 这三条结论，面试时可以这样讲

1. **我抓出了自己评测体系里的 3 个 bug**（可量化：受影响的用例数从 33/68 降到 0）。
   ——说明评测本身需要被验证，而不是拿来就用。

2. **修完后发现 LLM 跑分方差极大（同配置 54.4% vs 61.8%，全区间 54%–90%），
   所以我拒绝报单一数字，只报区间。**
   ——说明我知道自己的测量手段的局限。

3. **剩余失败里大部分是"拒绝在证据不足时动手"，而非推理错误。**
   ——说明我的评分口径**奖励猜中标签、惩罚谨慎**，这本身是需要修的设计缺陷。

## 四、面试必答清单（能答 8 条再往上写）

### 基础题（答不上就别写这个项目）

1. **你说的 L1 档位具体是什么？为什么不做全自动？**
   → L1 = 只读诊断自动、写操作必须人工确认。行业调研显示 98% 的企业只接受"有条件地让 AI 改生产"，仅 8.5% 接受全自动。而且 L1 档位下产品力不在"多自主"，而在"能不能把一次变更讲清楚"。

2. **三条安全不变量分别是什么？怎么保证不被绕过？**
   → 见版本 C。关键点：**不是靠提示词要求模型自觉，而是代码结构上做不到**。

3. **dry-run 解决了什么问题？**
   → K8s 原生支持服务端干跑：把变更发给集群校验但不执行。本项目强制要求，没过就不生成可执行方案——不让人去点一个注定失败的操作。

4. **你的评测用例怎么保证不是"自己出题自己考"？**
   → 两条：① 用大模型生成规则之外的对抗场景反测；② 接入 IBM ITBench 真实事故数据拿非自证分数。并且**主动承认**自造用例上的 100% 不能外推到生产。

### 进阶题（决定你是"做过"还是"想过"）

5. **为什么规则引擎比 LLM 准？那还要 LLM 干嘛？**
   → K8s 常见故障模式有限（就那么几类，Pod 状态和退出码里就有硬信号），确定性规则天然更准且零成本。LLM 的价值是**发现规则哪里不行**——5 个规则缺陷都是它暴露的。这是分工，不是能力问题。

6. **举一个你自己踩的坑。**
   → 我加过一条"日志里出现 connection refused 就判定依赖故障"的启发式，结果被一条无关的 metrics 上报失败噪声骗过，**让本该回滚能修好的场景变成"建议别动手"**。改成"只看进程终止原因那一行"才修好。教训：启发式规则在信号干净时最准、在嘈杂时最脆，每条启发式都得配一条对抗用例。

7. **你提到"假阳性"和"漏报"，哪个更严重？**
   → 假阳性更严重——不该动手时动手会主动造成伤害；漏报只是服务继续不可用。所以每条用例都标注"绝对不能提的动作"。

8. **归因优先级为什么重要？**
   → 配置 > 依赖 > 网络；集群级优先于工作负载级。顺序错了会把"自己配错"判成"对方挂了"，方向完全相反。这在实现时改了三遍才理顺。

### 送命题（答不上来会被认为简历造假）

9. **19 类故障签名具体是哪些？举 3 个说明判据。**
   → 必须能张口说出：如 `oom_killed` 用 `terminated.reason==OOMKilled` 或 `OOMKilling` 事件判定（**不能只看退出码 137**，因为探针误杀也是 137）；`service_target_port_mismatch` 用 Service 的 targetPort 与容器实际监听端口比对；`dependency_unavailable` 用"端口匹配但对方 Service 就绪后端为 0"判定。

10. **如果让你重做，你会改什么？**
    → 好的答案：把"配置层"排到第一优先级而不是最后——真实事故里配置类根因占比最大（ITBench 里 12/35），而我最初只做了 Pod 状态层。

## 六、客观定位：这算什么水平的项目

**坦白说**：这是一个**完成度明显高于普通个人项目**的作品。区别不在于用了 AI，而在于：

- 有**可复现的数字**（193 条测试、68 条用例、25 条对抗测试）
- 有**外部验证**（真实事故数据集）
- 有**主动披露的缺陷**（自造的假阳性、用例期望值写错）
- 有**成体系的文档**（PRD、立项材料、行业扫描、盲区报告、使用手册、入门必读）

**但短板也很明确**：

- **没有真实生产验证**——全部在本地沙箱，故障是自己注入的
- **没有真实用户**——采纳率、MTTR 改善都是"待测"
- **评测集是自造的**——68 条里只有 1 条来自现场采集

所以**最诚实的写法**是把它定位成"**一个把安全边界和评测体系做扎实的原型**"，
而不是"一个已经在生产跑通的系统"。前者可信，后者一问就穿。

## 七、最后一句

这个项目里**最值钱的不是"AI"两个字，是"知道自己哪里不行"**。

它能说清自己的盲区（`docs/rule-blindspots.md`）、能承认自己的用例期望值写错过、
能区分"自造用例 100%"和"真实数据 3/3"是两种不同性质的数字。

**面试时把这个态度讲出来，比多背两个技术名词有用得多。**
