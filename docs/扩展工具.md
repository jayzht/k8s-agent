# 扩展工具：写一个 provider 就行

> 加一个数据源 = 加一个类。**不动核心任何文件。**

## 30 秒版本

```python
# my_provider.py
from omagent.providers import Provider, ProviderTool
from omagent.tools import ToolSpec

class ChangeProvider(Provider):
    name = "change-mgmt"

    def available(self):
        return True, "内部变更系统 v2"        # 连不上就返回 (False, 原因)，注册表会跳过

    def tools(self):
        return [
            # ① 只读工具：给 call 就行 → 自动执行，不需要批准
            ProviderTool(
                ToolSpec("list_recent_changes", False, "列出最近的变更单",
                         {"type": "object",
                          "properties": {"namespace": {"type": "string"}},
                          "required": ["namespace"]}),
                call=lambda p: f"{p['namespace']} 最近 3 条变更：#1042 #1039 #1031",
            ),
            # ② 写工具：**必须**同时给 dry_run 和 apply → 自动纳入审批门禁
            ProviderTool(
                ToolSpec("open_rollback_ticket", True, "开一张回滚工单",
                         {"type": "object",
                          "properties": {"change_id": {"type": "string"},
                                         "rationale": {"type": "string"}},
                          "required": ["change_id", "rationale"]},
                         namespace_scoped=False),   # 调外部系统，不针对 K8s 命名空间
                dry_run=lambda p: (bool(p.get("change_id")),
                                   f"预检：变更单 {p['change_id']} 存在"),
                apply=lambda p: f"已开回滚工单，关联 {p['change_id']}",
            ),
        ]
```

装配：

```python
from omagent.providers import ProviderRegistry
agent = OpsAgent(k8s, audit, providers=ProviderRegistry([ChangeProvider()]))
```

只读工具进模型工具表、自动执行；写工具进模型工具表、**但调用只会生成审批卡片**，
和内置的 10 个写工具走完全同一条路（dry-run → 卡片 → 人工批准 → 重跑 dry-run → 执行 → 审计）。

## 三条硬规则（违反就在装配时抛异常，不是打日志放过）

| 规则 | 为什么 |
|---|---|
| **声明写工具就必须给 `dry_run` + `apply`** | 整个项目的承诺是「服务端干跑没过，人工批准也不执行」。一个提供不了无副作用预检的写工具没法纳入这条承诺。**这是刻意的门槛，不是"暂不支持"。** |
| **声明只读就不能带 `dry_run`/`apply`** | 声明和实现自相矛盾时不能猜哪个是真的。 |
| **只读工具必须有 `call`** | 否则模型调了会炸在运行期，不如装配期就失败。 |

还有一个默认值值得知道：`ToolSpec(namespace_scoped=...)` **默认 True**。也就是说
**新加的写工具默认会被"写操作命名空间白名单"约束**，不针对命名空间的操作
（节点级动作、调外部系统的工具）必须**显式**写 `namespace_scoped=False` 才豁免。
fail-closed 的方向不能反。

## provider 拿不到的能力（故意的）

- **不能绕过审批**：写工具一律进 `propose()` → 卡片 → 人工批准，没有"直接执行"的口子。
- **不能借到执行权**：MCP server 只暴露只读工具，写工具不上 MCP。
- **不能改内置读写切分**：`tools.py` 里那 25 个工具是静态的安全边界，不参与动态装配。

一句话：**扩展数据源不该降低系统的安全下限。** 加得越多，边界越要清楚。

## 这一层是怎么补出来的（一个值得讲的 bug）

provider 抽象我是分两步加的，第一步**只接了一半**——这个 bug 三层验证全都漏掉了：

**症状**：provider 的**只读**工具展示给了模型，但一调用就报
「工具 'query_metrics' 未登记，拒绝生成方案」。

**根因**：`session` 判断读写用的是**模块级**的 `tools.is_mutating()`，而它对
**未登记的工具默认返回 True**（这是刻意的 fail-closed 设计）。引入注册表之后，
provider 的只读工具不在静态表里 → 被判成写操作 → 走进 `propose()` →
而 `propose()` 只查静态表 → "未登记" 拒绝。

**为什么三层都没抓到**：

| 验证层 | 为什么漏了 |
|---|---|
| 单元测试 | 测的是注册表和 `agent.run_readonly()`，**没测 session 的路由** |
| 评测 | 15 个剧本跑的时候**不装配 provider** |
| 手工验证 | 我只收集了工具**名字**，没看 `ok` 字段——看到 `query_metrics` 出现在列表里就以为成功了 |

**修法**：把"这个工具是不是写操作"这个问题**交给注册表回答**，不再用只认静态表的
那个函数。`Agent.is_mutating()` 先查静态表、再查注册表、都没有才返回 True。

**教训**：fail-closed 是对的，但**"未登记 → 当写操作"这条规则在引入注册表之后
必须由注册表来回答**。加抽象层时，最容易漏的就是"原来那个判断在新世界里还成不成立"。

顺带修掉第二处同类问题：命名空间白名单原本是
`if spec.name in ("cordon_node", "uncordon_node", "drain_node")` ——
**硬编码工具名做例外**，加 provider 时根本不会跟着扩展。改成了 `ToolSpec.namespace_scoped`
字段，默认 True（受约束），要豁免得显式声明。
