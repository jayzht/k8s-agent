# 扩展工具：写一个 provider 就行

> 加一个数据源 = 加一个类。**不动核心任何文件。**

## 30 秒版本

```python
# my_provider.py
from omagent.providers import Provider, ProviderTool
from omagent.tools import ToolSpec

class ChangeProvider(Provider):
    name = "change-mgmt"

    def available(self):
        return True, "内部变更系统 v2"        # 连不上就返回 (False, 原因)，注册表会跳过

    def tools(self):
        return [
            # ① 只读工具：给 call 就行 → 自动执行，不需要批准
            ProviderTool(
                ToolSpec("list_recent_changes", False, "列出最近的变更单",
                         {"type": "object",
                          "properties": {"namespace": {"type": "string"}},
                          "required": ["namespace"]}),
                call=lambda p: f"{p['namespace']} 最近 3 条变更：#1042 #1039 #1031",
            ),
            # ② 写工具：**必须**同时给 dry_run 和 apply → 自动纳入审批门禁
            ProviderTool(
                ToolSpec("open_rollback_ticket", True, "开一张回滚工单",
                         {"type": "object",
                          "properties": {"change_id": {"type": "string"},
                                         "rationale": {"type": "string"}},
                          "required": ["change_id", "rationale"]},
                         namespace_scoped=False),   # 调外部系统，不针对 K8s 命名空间
                dry_run=lambda p: (bool(p.get("change_id")),
                                   f"预检：变更单 {p['change_id']} 存在"),
                apply=lambda p: f"已开回滚工单，关联 {p['change_id']}",
            ),
        ]
```

装配：

```python
from omagent.providers import ProviderRegistry
agent = OpsAgent(k8s, audit, providers=ProviderRegistry([ChangeProvider()]))
```

只读工具进模型工具表、自动执行；写工具进模型工具表、**但调用只会生成审批卡片**，
和内置的 23 个写工具走完全同一条路（dry-run → 卡片 → 人工批准 → 重跑 dry-run → 执行 → 审计）。

## 三条硬规则（违反就在装配时抛异常，不是打日志放过）

| 规则 | 为什么 |
|---|---|
| **声明写工具就必须给 `dry_run` + `apply`** | 整个项目的承诺是「服务端干跑没过，人工批准也不执行」。一个提供不了无副作用预检的写工具没法纳入这条承诺。**这是刻意的门槛，不是"暂不支持"。** |
| **声明只读就不能带 `dry_run`/`apply`** | 声明和实现自相矛盾时不能猜哪个是真的。 |
| **只读工具必须有 `call`** | 否则模型调了会炸在运行期，不如装配期就失败。 |

还有一个默认值值得知道：`ToolSpec(namespace_scoped=...)` **默认 True**。也就是说
**新加的写工具默认会被"写操作命名空间白名单"约束**，不针对命名空间的操作
（节点级动作、调外部系统的工具）必须**显式**写 `namespace_scoped=False` 才豁免。
fail-closed 的方向不能反。

## provider 拿不到的能力（故意的）

- **不能绕过审批**：写工具一律进 `propose()` → 卡片 → 人工批准，没有"直接执行"的口子。
- **不能借到执行权**：MCP server 只暴露只读工具，写工具不上 MCP。
- **不能改内置读写切分**：`tools.py` 里那 41 个工具（18 只读 + 23 写）是静态的
  安全边界，不参与动态装配。
- **不能碰禁区清单**：`FORBIDDEN` 里那 8 个动作既不进 provider 注册表，
  也不受 `--allow-tool` 影响——那条开关只认内置的 `UNLOCKABLE`。

一句话：**扩展数据源不该降低系统的安全下限。** 加得越多，边界越要清楚。

---

## `--allow-tool`：内置禁区动作的解锁开关（**provider 走不了这条路**）

默认有 8 个动作是禁止的（`delete_pvc`、`delete_pv`、`delete_namespace`、
`modify_rbac`、`exec_in_pod`、`read_secret`、`apply_manifest`、`delete_workload`）。
其中一部分可以在启动时**逐个**显式解锁：

```bash
omagent serve --allow-tool delete_pvc
```

它和 provider 扩展是**两条完全不同的路**，别混：

| | `--allow-tool`（解锁内置） | provider（自己写类） |
|---|---|---|
| 打开的是什么 | `tools.py` 里**已经写好**的禁区动作 | 你新写的工具 |
| 能不能加任意动作 | ❌ 只能解锁 `UNLOCKABLE` 里登记的 | ✅ 随便写 |
| 准入门槛 | 必须在 `K8sClient.apply_mutation` 里有实现（有测试钉住） | 写工具必须同时给 `dry_run` + `apply` |
| 危险档位 | `delete_pvc` 是 `severe`，批准要**手输目标名字** | 由你自己的 `ToolSpec.danger` 决定 |
| 默认状态 | **锁着**，不写参数就一个字都不可用 | 装配了就在（写工具仍要审批） |

几条刻意的设计：

1. **默认锁着，一个名字一个开关。** 不做 `--unsafe` 全开——8 个动作的风险
   差着量级，合并成一个是替运维做决定，审计里也分不出他到底开了哪个。
2. **能解锁哪些由代码决定**（`UNLOCKABLE`），不是配置项。而且每个可解锁的动作
   都必须在 `apply_mutation` 里有实现，否则解锁出来的是"看得见、一提就报未实现"
   的空壳——这条有源码级测试钉着。
3. **三个永久打不开**：`delete_namespace` / `modify_rbac` / `exec_in_pod`
   （`PERMANENTLY_FORBIDDEN`）。它们不是"还没实现"，是"实现了也不该有这条路"。
4. **解锁不等于免审批。** 解锁的是"模型能不能提议"，不是"能不能直接执行"。
   解锁后的动作照样走审批卡片、dry-run 复跑、命名空间白名单、审计链；
   而且它连只读路径都进不去（`run_readonly()` 会拒）。
5. **启动时大声回显**：解锁了什么、各自什么风险，都打在启动日志和
   `omagent tools` 的输出里。禁区工具被打开是这台机器上最该被记住的一条配置，
   不能只存在于某个人的命令行历史里。

> ⚠️ 一个真踩过的坑，值得所有"往模型手里加工具"的人记住：
> `delete_pvc` 的工具描述里原本写了「默认锁着，需 `--allow-tool delete_pvc`」。
> 模型读到的是「这个工具现在是锁着的」，于是**它明明看得见却不提卡片**，
> 还回一句"我没有删除类工具"。**工具描述只该描述这个动作做什么，
> 不该描述怎么开启它**——开启方式是给运维看的，写在 `--help` 和这个文档里。

## 这一层是怎么补出来的（一个值得讲的 bug）

provider 抽象我是分两步加的，第一步**只接了一半**——这个 bug 三层验证全都漏掉了：

**症状**：provider 的**只读**工具展示给了模型，但一调用就报
「工具 'query_metrics' 未登记，拒绝生成方案」。

**根因**：`session` 判断读写用的是**模块级**的 `tools.is_mutating()`，而它对
**未登记的工具默认返回 True**（这是刻意的 fail-closed 设计）。引入注册表之后，
provider 的只读工具不在静态表里 → 被判成写操作 → 走进 `propose()` →
而 `propose()` 只查静态表 → "未登记" 拒绝。

**为什么三层都没抓到**：

| 验证层 | 为什么漏了 |
|---|---|
| 单元测试 | 测的是注册表和 `agent.run_readonly()`，**没测 session 的路由** |
| 评测 | 22 个剧本跑的时候**不装配 provider** |
| 手工验证 | 我只收集了工具**名字**，没看 `ok` 字段——看到 `query_metrics` 出现在列表里就以为成功了 |

**修法**：把"这个工具是不是写操作"这个问题**交给注册表回答**，不再用只认静态表的
那个函数。`Agent.is_mutating()` 先查静态表、再查注册表、都没有才返回 True。

**教训**：fail-closed 是对的，但**"未登记 → 当写操作"这条规则在引入注册表之后
必须由注册表来回答**。加抽象层时，最容易漏的就是"原来那个判断在新世界里还成不成立"。

顺带修掉第二处同类问题：命名空间白名单原本是
`if spec.name in ("cordon_node", "uncordon_node", "drain_node")` ——
**硬编码工具名做例外**，加 provider 时根本不会跟着扩展。改成了 `ToolSpec.namespace_scoped`
字段，默认 True（受约束），要豁免得显式声明。

# 第二种扩展方式：接别人的 MCP server

上面那种是"自己写 provider 类"。如果你只是想把**别人已经写好的**工具接进来，
那连类都不用写——直接用 MCP 客户端：

```bash
omagent serve \
  --mcp-server "fs=npx -y @modelcontextprotocol/server-filesystem /data" \
  --mcp-server "github=npx -y @modelcontextprotocol/server-github" \
  --mcp-allow-read fs:read_file \
  --mcp-allow-read github:list_issues
```

启动横幅会显示：

```
数据源：fs（1 个只读工具）
数据源：github（1 个只读工具）
```

工具在模型那边叫 `fs__read_file`、`github__list_issues`（加前缀避免两个 server 重名）。

## ⚠️ 不给 `--mcp-allow-read`，那个 server 的工具**一个都不会导入**

这不是保守，是必须的。MCP 协议里远程工具可以自报 `annotations.readOnlyHint`，
但**那只是对端的一句话**。一个写坏了的、被入侵的、或者干脆恶意的 server，
完全可以把 `delete_everything` 标成只读，然后骗过自动执行。

所以本项目的规则是：

> **对端的自述一律不采信，必须由人来点名。**

我的测试里就放了一个这样的 fixture 来钉住这条边界——它把 `delete_everything`
标成 `readOnlyHint: True`，客户端照样不导入它。

## 为什么外部工具**不能**改集群

被导入的远程工具一律当只读。你可能会想"我想要个能改集群的外部工具"——
做不到，而且是刻意的：

本项目的写路径有一个硬要求：**必须能无副作用预检（dry-run）**。
任意一个远程 MCP 工具都没法提供这个保证（协议里没有这个概念）。
让没有 dry-run 的工具进写路径，就等于放弃「干跑没过就不执行」这条承诺。

所以取舍很清楚：**接外部工具不会削弱安全边界，代价是外部工具只能读。**
想要能改集群的扩展，用上面那种 provider 方式写，把 `dry_run` / `apply` 补上。

## 远端返回值同样是不可信输入

外部工具吐回来的内容和集群日志一视同仁——自动围栏化 + 注入计分。这不是额外实现，
而是因为安全层挂在**工具结果回灌**这个边界上，不是挂在每个工具上，
所以新接进来的数据源**自动**获得防护，不会有人忘记加。

## 支持的传输

stdio（spawn 子进程、按行 JSON-RPC）。官方和社区绝大多数 MCP server 都是 stdio：
filesystem、github、postgres、slack、puppeteer…

起不来的 server 只会被**跳过**并在启动横幅里写明原因，不影响其它工具——
外部依赖缺失是功能降级，不是启动失败。

## 附：一次真实第三方 MCP server 的实测记录

> 这一节是**实测记录**，不是设计说明。目的是让"能接入外部工具"这句话有据可查。

**被测对象**：官方的 `@modelcontextprotocol/server-filesystem`
（`repository: github.com/modelcontextprotocol/servers`，v1.0.0），
通过 `npx`/`node` 以 stdio 启动，暴露一个目录。

**配置**（一条命令，运行时从界面或 CLI 加）：

```bash
omagent serve --mcp-server "opsdocs=node <path>/dist/index.js <手册目录>" \
              --mcp-allow-read opsdocs:list_directory \
              --mcp-allow-read opsdocs:read_text_file \
              --mcp-allow-read opsdocs:search_files
```

**结果**：

| 环节 | 结果 |
|---|---|
| 工具发现 | 服务端暴露 **14 个工具**（read_file / read_text_file / list_directory / search_files / …） |
| 默认拒绝 | 不写 `--mcp-allow-read` → **导入 0 个**；界面上 11 个被跳过并逐条写明"没在只读白名单里" |
| 白名单 | 点名 3 个 → 只导入这 3 个，名称加 `opsdocs__` 前缀避免撞名 |
| 只读约束 | 3 个在注册表里都是 `mutating=False`，`is_mutating()` 返回 False |
| 真实调用 | `list_directory` / `read_text_file` 都成功执行，读回的内容完整 |
| **模型会不会用** | 问"P0 该通知谁、大促能不能改配置"，模型**主动调了** `opsdocs__list_directory` + `opsdocs__read_text_file`，并答出了只存在于那个文件里的内部事实（值班经理姓名、分机、15 分钟规则、变更冻结窗口） |
| **注入防线是否覆盖** | 在文件里埋一条注入载荷后单独验证：`safety.scan` 命中 2 条、总分 6（阈值 3），`wrap()` 打上 `<untrusted>` 围栏，**原文完整保留**。也就是说外部 MCP 作为新入口，防线是覆盖到的 |
| 副作用 | 模型在回答末尾**主动**说明"这份手册是从集群读出的文件、包在 `<untrusted>` 里" —— 围栏对它是可见的 |

**两点仍然要知道的边界**：

1. 只实测了**一个** server（filesystem）。协议层是手写的 JSON-RPC，别的 server 若用了
   这个实现没覆盖的能力（sampling / roots / 流式通知），不保证能用。
2. 默认**零导入**意味着"装上就有一堆工具"这个体验是没有的——每个 server、每个工具
   都得由人点名。这是刻意的（MCP 的 `readOnlyHint` 只是对端的一句话，不能当凭据），
   但也确实比开箱即用的集成多一步配置。
