# 这套系统覆盖了运维人员多少工作内容

> 面试会问「这能替代运维吗」。**标准答案是：不能，它覆盖的是一段工作流，不是一个岗位。**
> 下面是可以直接拿去答的分解。
>
> ⚠️ 本文按**当前代码**写（`src/omagent/tools.py` / `patrol.py` / `mcp_client.py` /
> `evals.py`）。早先版本曾写「告警巡检基本没有」「写工具只有 10 个」
> 「配置类改不了」——**这三条现在都不成立了**，下文已按现状重写。

---

## 一句话

**它覆盖的是「从发现问题 → 到给出一个可批准的方案」这一段。**
按工作量粗算，K8s 运维的日常里它大概沾到 **15%~25%**——但更准确的说法是
**它覆盖了一段工作流，不是工作量的百分比。**

而且它**不减少工作量，它压缩的是"查证"这一步的成本**：
原来要敲十几个 kubectl、翻文档、问同事，现在一次对话。

> 「发现问题」这一段以前是空缺，现在**补上了一半**：
> 能接 Alertmanager 告警、能定时主动巡检，但**只自动触发只读调查**，
> 产出仍然是一张待批卡片（见下）。

---

## 当前能力快照（先看这几个数）

| 维度 | 当前值 |
|---|---|
| 内置只读工具 | **15 个**（`get_*` + `search_cases`），自动执行、不需要批准 |
| 内置写工具 | **14 个**，全部要人工批准 |
| 只读 provider 工具 | 最多 **5 个**：Prometheus 3（`query_metrics`/`get_alerts`/`get_targets`）+ Loki 1（`query_logs`）+ 发布历史 1（`get_recent_changes`，默认总开） |
| 外部 MCP 只读工具 | **可显式导入**（默认一个都不导入，必须由人点名白名单） |
| 硬禁止动作 | **8 个**（见下），谁批准都执行不了 |
| 诊断评测 | 15 个剧本；**最新单跑 14/15，历史 12~15/15** |
| 巡检/告警 | Alertmanager webhook + 主动巡检；**只触发只读调查**，不发通知 |

## 逐项对照

| 运维工作内容 | 占比 | 覆盖度 | 具体 |
|---|---|---|---|
| **监控告警响应 / 巡检** | ~30% | ⚠️ **补上了一半** | 有 Alertmanager webhook（`POST /api/alert`）和主动巡检（`patrol.py`，`--patrol-interval`）：先做**确定性预筛**（零模型成本），只对异常工作负载起调查；同目标有**冷却去重**。但**只自动触发只读调查，产出仍是待批卡片**；不会发通知，也不做告警的降噪/静默/路由 |
| **故障诊断（查根因）** | ~20% | ✅ **最强的一段** | 15 个剧本，**最新单跑 14/15、历史 12~15/15**；15 个内置只读工具 + 最多 5 个只读 provider 工具，**还能接外部 MCP 只读工具**；能自己算「最近改了什么」；可检索 runbook |
| **故障处置** | ~20% | ⚠️ **14 个写工具，且必须人批** | 见下节清单。含后来补上的 **4 个配置类工具**；`danger` 只影响卡片摩擦强度，**不是准入分级** |
| **变更管理（发布/回滚/灰度）** | ~15% | ⚠️ **只有回滚** | `rollout_undo` / `rollback_configmap` 可以；**发布不行**（`apply_manifest` 在禁止清单里）；灰度/CD 完全没有 |
| **容量与成本** | ~5% | ❌ 没有 | 能读 ResourceQuota / 资源用量 / HPA 状态，**不能改配额、不能做容量规划、不算钱** |
| **稳定性建设（PDB/探针/配额规范）** | ~5% | ⚠️ **能改一部分了** | 探针端口、nodeSelector、Service selector / targetPort 都能改；**PDB 和 ResourceQuota 改不了** |
| **工单 / 文档 / 交接 / 复盘** | ~5% | ❌ 没有 | 有审批卡片和审计链，但工单系统、文档、复盘报告都没有 |
| **集群生命周期（建集群/升级/节点运维/备份/安全加固）** | — | ❌ **零** | 完全没碰 |

## 能改的 14 个动作

```
# 让现状恢复类
rollout_restart     rollout_undo       scale_workload     delete_pod
patch_resources     patch_hpa          rollback_configmap
cordon_node         uncordon_node      drain_node

# 后来补上的 4 个配置类修复
patch_service_selector   patch_service_port   patch_probe   patch_node_selector
```

那 4 个配置类工具是补上评测里「症状像重启、其实重启没用」那几个陷阱场景的正解。
但它们**不是"随便改 YAML"**——能改的字段是枚举出来的（selector、targetPort、
探针端口、nodeSelector 的增删），除此之外表达不了。

**每个写操作都必须人工批准**：一张带影响面、dry-run 结果、回滚方式和
`rationale` 的确认卡片。`danger=caution` 的再加醒目警告。
**目前没有任何工具是 `severe`**——那个「必须手输目标名字才能批准」的档位是为
将来解锁禁区工具预留的，**还没被真实使用过，不能当成已验证的能力讲**。

## 明确做不到的（这才是重点）

### 1. 不能发布、不能改任意 YAML

`apply_manifest` 在禁止清单里。所有写能力都是**参数化工具**——
「改一段任意 YAML」这件事**根本表达不了**。所以镜像变更、灰度发布、CD
都不在范围内，只能靠回滚退回去。

### 2. 不碰 HPA 的 scaleTargetRef

`patch_hpa` 只能改 `minReplicas` / `maxReplicas`，**改不了 scaleTargetRef**。
这是当前 15 个评测剧本里**唯一一个"正解就是明说我没有工具"的场景**（`hpa`）。
（早先 `selector` / `port` / `probe` / `pending` 也属于这一类，
但那 4 个场景**现在都有对应的参数化工具了**——这是这批能力里最实质的一次扩面。）

### 3. 不做任何危险动作（8 个硬禁止）

```
delete_workload   delete_namespace   delete_pvc   delete_pv
modify_rbac       read_secret        exec_in_pod  apply_manifest
```

`modify_rbac` 是提权路径，`read_secret` 会碰凭据，`exec_in_pod` 等于把集群交出去，
`apply_manifest` 是「参数化之外的口子一律不开」。**它们根本不出现在模型可见的
工具清单里**，谁批准都执行不了。

### 4. 告警只进不出

能接 Alertmanager webhook、能主动巡检、能查 Prometheus 里正在 firing 的告警；
但**不会主动发通知**（没有 Slack / 钉钉 / 邮件集成），也不做告警的降噪、静默、
路由——那是监控系统自己的事。它只是把「有人发现了」提前到「它自己扫到了」。

### 5. 批准之后，全是人

没有自动执行、没有自愈、没有 L2/L3。写操作执行完，事情就交回给人。
也**没有降级路径**：模型服务不可用时它只能报错、请人手工处理。

### 6. 不碰集群之外的世界，而且是单集群

云资源、网络、DNS、证书、CI/CD、镜像仓库、数据库内部——全都不在范围内。
而且**只支持单集群**：没有多集群、没有高可用；角色只有 operator / viewer，
没有「某人只能动某个命名空间」这种粒度。

## 更准确的定位（建议这么说）

> 它不是"运维助手"，是**运维人员的取证与执行代理**：
> 覆盖「症状 → 证据 → 一个可批准的方案」这段，**不覆盖"批准之后"**。
>
> 它替代的不是运维，是**查证时敲命令和翻文档的那十几分钟**。

一个具体对比：

|  | 手工 | 用它 |
|---|---|---|
| 发现故障 | 告警 / 巡检 | **接告警 + 主动巡检**（这一段补上了一半） |
| 查根因 | 十几个 kubectl + 翻日志 + 问同事 | 一次对话，**只读工具自动执行** |
| 决定怎么办 | 人判断 | 模型给方案，**人判断**（一样） |
| 执行 | 人敲命令 | 人点批准确认卡，**执行前后都有审计** |
| 复盘 | 靠记忆 | 审计链 + 案例库 |

**中间两步是它真正改的地方。**

## 如果要扩大覆盖，按性价比排

| 加什么 | 覆盖什么 | 难度 |
|---|---|---|
| **通知推送**（Slack / 钉钉） | 把结论和卡片推给人，补上"告警只进不出" | 小 |
| **工单系统集成** | 处置完自动开工单 / 留复盘材料 | 小 |
| **更多参数化写工具**（HPA scaleTargetRef、ResourceQuota、PDB） | 把剩下"只能明说没工具"的场景补掉 | 中，每个都要能过 dry-run |
| **告警侧能力**（静默 / 路由 / 降噪） | 从"接告警"走到"参与告警治理" | 中，且要先想清楚这该不该由本系统做 |
| **多集群** | 从单集群到多集群 | 大，且会放大权限与审计的复杂度 |

> 一条取舍要记住：**加只读数据源几乎不增加风险，加写工具会直接放大"误伤"的面积**。
> 所以每加一个写工具，都得先在评测里配一条反向对照，证明它不会在该动手时乱动。

## ⚠️ 面试时绝对不要说的

| 别说 | 为什么 |
|---|---|
| "能替代运维" | 上面那张表摆着呢，一问就穿 |
| "覆盖运维 80% 的工作" | 差得远，而且这个数字编不出来 |
| "生产级" | 单集群 demo，社区为 0 |
| "通过率 100%" | 最新单跑是 14/15，历史 12~15/15；单次满分不是稳态 |

**要说的是**：它把一段工作流做扎实了（诊断最新 14/15），而且**清楚地知道自己不该做什么**——
8 个禁止动作、写操作必须人批、巡检只触发只读调查、扩展数据源不能削弱安全边界。
**"知道边界在哪"本身就是这个项目最有说服力的地方。**
