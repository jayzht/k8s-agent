# 这套系统覆盖了运维人员多少工作内容

> 面试会问「这能替代运维吗」。**标准答案是：不能，它覆盖的是一段工作流，不是一个岗位。**
> 下面是可以直接拿去答的分解。
>
> ⚠️ 本文按**当前代码**写（`src/omagent/tools.py` / `k8s.py` / `capacity.py` /
> `patrol.py` / `evals.py`）。早先版本曾写「告警巡检基本没有」「写工具只有 10 个」
> 「配置类改不了」——**这三条现在都不成立了**，下文已按现状重写。
> 同一轮里又更新掉两条：「HPA 的 scaleTargetRef 改不了」和「没有任何工具是
> `severe`」——现在前者有 `patch_hpa_target`、后者有解锁出来的 `delete_pvc`。
> **再往后一轮又推翻了两条**：「变更管理只有回滚」（现在有发布和灰度）和
> 「容量与成本完全没有」（现在有余量、成本、改配额、改 PDB）。
> 本文里凡是写「当前值」的地方，数字都以**代码**为准，不是记忆。

---

## 一句话

**它覆盖的是「从发现问题 → 到给出一个可批准的方案」这一段。**
按工作量粗算，K8s 运维的日常里它大概沾到 **15%~25%**——但更准确的说法是
**它覆盖了一段工作流，不是工作量的百分比。**

而且它**不减少工作量，它压缩的是"查证"这一步的成本**：
原来要敲十几个 kubectl、翻文档、问同事，现在一次对话。

> 「发现问题」这一段以前是空缺，现在**补上了一半**：
> 能接 Alertmanager 告警、能定时主动巡检，但**只自动触发只读调查**，
> 产出仍然是一张待批卡片（见下）。

## 当前能力快照（先看这几个数）

| 维度 | 当前值 |
|---|---|
| 内置只读工具 | **18 个**（`get_*` + `rollout_history` + `search_cases`），自动执行、不需要批准 |
| 内置写工具 | **23 个**，全部要人工批准 |
| 默认锁着的可解锁动作 | **1 个**：`delete_pvc`（`danger="severe"`，需 `--allow-tool delete_pvc` 显式解锁） |

| 诊断评测 | **16 个剧本**（新增 `capacity`）。**最新一次干净全量单跑 16/16**（`--settle 22`，查证/避坑/动作 100%/100%/100%，抗注入 1/1，720.0s / 686,111 token）；但**新题库只跑过这一次**，历史区间仍是旧题库的 **12~15/15**（**不要报 100%**）。改预期前先跑的第一次是 9/16，原因见 `docs/eval-report.md` 第十一轮 |
| 巡检/告警 | Alertmanager webhook + 主动巡检；**只触发只读调查**，不发通知 |
| 单元测试 | **422 条**（`pytest tests/`，全绿） |

## 逐项对照

| 运维工作内容 | 占比 | 覆盖度 | 具体 |
|---|---|---|---|
| **监控告警响应 / 巡检** | ~30% | ⚠️ **补上了一半** | 有 Alertmanager webhook（`POST /api/alert`）和主动巡检（`patrol.py`，`--patrol-interval`）：先做**确定性预筛**（零模型成本），只对异常工作负载起调查；同目标有**冷却去重**。但**只自动触发只读调查，产出仍是待批卡片**；不会发通知，也不做告警的降噪/静默/路由 |
| **故障诊断（查根因）** | ~20% | ✅ **最强的一段** | 16 个剧本，**最新一次干净全量单跑 16/16、历史区间 12~15/15（旧题库）**；18 个内置只读工具 + 最多 5 个只读 provider 工具，**还能接外部 MCP 只读工具**；能自己算「最近改了什么」；可检索 runbook |
| **故障处置** | ~20% | ⚠️ **23 个写工具，且必须人批** | 见下节清单。含后来补上的 **4 个配置类工具**、**`patch_hpa_target`**、**变更管理 6 个**、**容量成本 2 个**；`danger` 只影响卡片摩擦强度，**不是准入分级** |
| **变更管理（发布/回滚/灰度）** | ~15% | ⚠️ **能发布、能回滚、能手搓灰度；但没有 CD、没有自动渐进式发布** | 发布：`patch_image`（JSON patch 精确改镜像）+ `patch_configmap`；回滚：`rollout_undo` / `rollout_undo_to` / `rollback_configmap`；灰度：`canary_start` / `canary_promote` / `canary_abort`。⚠️ 金丝雀是**按就绪副本数加权**的灰度，不是按请求数精确切分。**不是 CD**：没有流水线、没有自动渐进式发布/自动判定、没有多环境编排；`apply_manifest` 仍在禁止清单里，**变更还是只能走参数化工具** |
| **容量与成本** | ~5% | ⚠️ **能算余量、能估成本，但成本依赖人工填的价格表** | `get_capacity`（可分配 vs 已预留 requests vs 实际使用、还能调度多少、配额使用率、预留最多的负载）、`get_cost`（预留花销 / 按命名空间与工作负载拆分 / 闲置成本）、`patch_resourcequota`、`patch_pdb`。⚠️ **不调云计费 API、不内置价格**：没有 `var/pricing.json` 就**不算钱**、只说明怎么配；用示例价会显式警告。计价口径是 **requests（预留量）**，不是实际用量 |
| **稳定性建设（PDB/探针/配额规范）** | ~5% | ⚠️ **能改一部分了** | 探针端口、nodeSelector、Service selector / targetPort 都能改；**PDB（`patch_pdb`）和 ResourceQuota（`patch_resourcequota`）现在也能改了** |
| **工单 / 文档 / 交接 / 复盘** | ~5% | ❌ 没有 | 有审批卡片和审计链，但工单系统、文档、复盘报告都没有 |
| **集群生命周期（建集群/升级/节点运维/备份/安全加固）** | — | ❌ **零** | 完全没碰 |

## 能改的 23 个动作

```
# 让现状恢复类（11）
rollout_restart     rollout_undo       scale_workload     delete_pod
patch_resources     patch_hpa          patch_hpa_target   rollback_configmap
cordon_node         uncordon_node      drain_node

# 配置类修复（4）
patch_service_selector   patch_service_port   patch_probe   patch_node_selector

# 变更管理：发布 / 回滚到指定版本 / 金丝雀灰度（6）
patch_image   patch_configmap   rollout_undo_to
canary_start  canary_promote   canary_abort

# 容量与成本（2）
patch_resourcequota   patch_pdb
```

那 4 个配置类工具是补上评测里「症状像重启、其实重启没用」那几个陷阱场景的正解。
`patch_hpa_target` 是补上「HPA 的扩缩容目标被改坏」——它的正解从
"我没有工具" 变成了"把 scaleTargetRef 改回去"。

**变更管理这一组回答的是"怎么安全地换版本"，而不是"怎么修坏掉的对象"。**
- `patch_image` 是**发布的原语**：用 JSON patch 精确定位到
  `/spec/template/spec/containers/<idx>/image`，**不整块替换 pod template**——
  整块替换是拿一份读到的旧快照写回去，会顺手抹掉这期间别人对同一个 template 的改动，
  还会把上一次没滚干净的字段一起带过去。容器名找不到时它会**报出现有容器名列表**；
  `dry is None`（真执行）时**执行后复查**，没生效就如实说"这次改动没有生效"。
- `patch_configmap` 管发布时的配置变更，`remove` 走 JSON patch（merge patch 删不掉
  map 里已有的键）；返回值里明确提醒"**改 ConfigMap 不会自动让 Pod 生效**"。
- 回滚有两条：`rollout_undo`（上一版）和 `rollout_undo_to`（**指定 revision**，
  revision 用只读的 `rollout_history` 查）。后者复用了 `_rollout_undo` 的
  "merge patch 删不掉新增字段、没滚干净要报出来"的检查。
- 灰度是 `canary_start` / `canary_promote` / `canary_abort` 三件套。

但它们**不是"随便改 YAML"**——能改的字段是枚举出来的（selector、targetPort、
探针端口、nodeSelector 的增删、HPA 的 scaleTargetRef、镜像、ConfigMap 键值、
配额上限、PDB 的 minAvailable/maxUnavailable），除此之外表达不了。

**金丝雀的两个设计点，必须一起讲，不能只讲好听的：**

1. **金丝雀名字固定是 `<name>-canary`，不接受参数。** 一旦名字能由参数决定，
   `canary_promote` / `canary_abort` 就得先反问"你说的是哪个金丝雀"，
   而模型完全可以把名字指到**别的**工作负载上——那不是灰度，是误操作。
   名字由输入推导出来，动作就不可能落到工具作者没想到的对象上。
2. **这是按副本数加权、不是按请求数加权。** 把稳定版 Deployment 克隆成
   `<name>-canary`，只改镜像，**标签与稳定版完全一致**（额外加一个
   `omagent-role: canary`），于是 Service 同时选中两者，流量按 Endpoints 里的
   **就绪副本数比例**分配——3:1 的副本比 ≈ 25% 流量给金丝雀，**前提是金丝雀 Pod
   真的 Ready**（没 Ready 就不进 Endpoints）。**不要把它吹成"精确流量切分"。**

`patch_pdb` 有一个容易踩的类型坑：`minAvailable` / `maxUnavailable` 是
**IntOrString**，`"50%"` **必须原样保留**，不能被 `int()` 吃掉；两者**互斥**；
既不是数字也不是百分比要报错。（PDB 是**唯一**能拦住节点排空打挂服务的东西，
所以这个类型不能糊弄。）

**每个写操作都必须人工批准**：一张带影响面、dry-run 结果、回滚方式和
`rationale` 的确认卡片。`danger=caution` 的再加醒目警告；
`danger=severe` 的（当前只有解锁出来的 `delete_pvc`）**必须手输目标名字才能批准**。

> `severe` 档位曾经是"预留但从未被走过"的死分支。现在它**第一次被真实使用并
> 在浏览器里验证过了**（`tests/e2e_frontend.py::test_severe_gate`：卡片头标 severe、
> 危险横幅、手输确认框、未输入禁用、**输错仍然禁用**、输对解锁、改回错的重新锁上）。
> 验证它需要服务用 `--allow-tool delete_pvc` 启动。

## 明确做不到的（这才是重点）

### 1. 不能改任意 YAML —— 变更**仍然只能走参数化工具**

`apply_manifest` 在禁止清单里，而且**解不开**（还没有安全实现）。所有写能力都是
**参数化工具**——「改一段任意 YAML」这件事**根本表达不了**。

这一条以前接的是"所以镜像变更、灰度发布都不在范围内"。**现在那半句不成立了**：
换镜像有 `patch_image`、指定版本回滚有 `rollout_undo_to`、灰度有 `canary_*`。
但**边界没有松动**——这三个能力各自都是**窄工具**，不是把 `apply_manifest` 打开了。
想改一个枚举之外的字段，系统仍然只有一句话：请你手工执行。

### 2. 变更管理的覆盖缺口：**发布 / 灰度那 4 个工具 + `patch_pdb` 零剧本**

这一条必须主动写出来，否则会让人误以为新工具都过了评测。先把范围说准——
**不是"那 7 个都完全没碰过"：**

| 工具 | 评测现状 |
|---|---|
| `patch_configmap` | ✅ 进了 `config` 的 `expect`，run15 真的提了它 |
| `rollout_undo_to` | ⚠️ 在 6 个"回滚"场景里被**等价认下**（带 revision 校验），但**没有剧本专门考"回滚到指定的更早版本"** |
| `rollout_history` | ⚠️ 作为**前置读取**被调用了 8 次，但只读依赖不等于"答案被考过" |
| `patch_image` | ❌ **零剧本**——而它是"发布"的原语 |
| `canary_start` / `canary_promote` / `canary_abort` | ❌ **零剧本**——灰度整条路径没被考过 |
| `patch_pdb`（容量成本组） | ❌ **零剧本** |

`patch_image` / `canary_*` 这 4 个只有**手动端到端验证**：

- 金丝雀全流程在演示集群上真跑过一遍：创建 → 标签订阅验证 → 重复创建被拒 →
  撤销不动稳定版 → 清理。
- **但"我手工跑通过"和"评测覆盖了"是两回事。** 手工验证证明的是"这条路径能走通"，
  证明不了"模型在该用的时候会想起它、不该用的时候不会乱用"。
  第四轮已经吃过一次教训：加了工具 ≠ 模型会用。

为什么没配剧本，理由也要写清楚：**给它们配剧本需要在 `sandbox/faults.sh` 里
造"坏发布 / 需要灰度的场景"**（比如发布一个新镜像把服务打挂、需要灰度观察），
这轮没做。所以现状是：**功能落地了，评测覆盖没跟上**——这条缺口留在台面上。

### 3. 有发布原语，但**没有 CD**

`patch_image` / `canary_*` 是"变更的动作"，不是"变更的流程"。没有的东西：

- **没有流水线**（不接 CI/CD、不触发构建、不管制品）。
- **没有自动渐进式发布**：不会"先放 5% 观察 5 分钟、指标不达标自动回退"。
  灰度是**人起、人看、人决定转正还是撤销**——`canary_promote` / `canary_abort`
  都得人批。
- **没有多环境编排**（staging → prod 的晋级链）。
- **没有自动判定**：转正的依据是人的观察，不是系统读到的指标。

换句话说：它把"安全地按一下发布/回滚/灰度"做成了受审批的窄动作，
**没有把"发布这件事"自动化**。这是刻意的——自动渐进式发布要接指标判定和回滚编排，
那是另一个系统的体量。

### 4. HPA 的 scaleTargetRef —— **现在能修了**（这条以前是"做不到"）

以前 `patch_hpa` 只能改 `minReplicas` / `maxReplicas`，改不了 `scaleTargetRef`，
所以 `hpa` 场景的正解是"我没有工具"。**现在补上了 `patch_hpa_target`**：
整块替换 `scaleTargetRef`，评测里 `hpa` 的 `expect` 从 `∅` 变成 `{patch_hpa_target}`，
同时把 `patch_hpa` 设成**陷阱**（目标指错时改副本区间治不了，属于"看着在处置、
其实什么也没修"）。

> 也就是说：**"剧本里唯一一个正解=明说没工具的场景"这句话已经不成立了。**
> 当年属于这一类的 `selector` / `port` / `probe` / `pending` 也都已有了参数化工具；
> `quota` 的正解也从"缩容止血"变成了"改配额（`patch_resourcequota`）根治，
> 缩容仍算通过"。真正"只能明说没工具"的，现在只剩禁止清单里的动作。
>
> ⚠️ 但 16 个剧本里**确实还有一个 `expect=∅`**——就是这轮新增的 `capacity`。
> 它的空集**不是因为"没工具"**，而是因为**没有故障、什么都不该改**（见下节）。

### 5. 默认不做危险动作（8 个默认拒绝，其中 1 个可显式解锁）

```
delete_workload   delete_namespace   delete_pvc   delete_pv
modify_rbac       read_secret        exec_in_pod  apply_manifest
```

这 8 个**默认根本不出现在模型可见的工具清单里**。但要分清三种状态：

| 状态 | 有哪些 | 说明 |
|---|---|---|
| **可显式解锁** | `delete_pvc` | 启动时 `--allow-tool delete_pvc`，解锁后仍要审批，且 `severe` 手输名字 |
| **永久禁止** | `delete_namespace`、`modify_rbac`、`exec_in_pod` | 任何参数都打不开——它们破坏的是**架构前提**（提权 / 破边界） |
| **还没有安全实现** | `apply_manifest`、`delete_pv`、`delete_workload`、`read_secret` | 仍在禁止清单里，现在也解不开——因为还没写出可审的实现 |

`modify_rbac` 是提权路径，`read_secret` 会碰凭据，`exec_in_pod` 等于把集群交出去，
`apply_manifest` 是「参数化之外的口子一律不开」。
**解锁 `delete_pvc` 不等于 dry-run 能兜住它**：服务端对删除的 dry-run
**不校验任何后果**（实测：删一个正在被 Pod 使用的 PVC，`--dry-run=server`
照样返回成功），所以它的安全边界是「默认锁着 + severe 手输名字 + 审计」，
**不是 dry-run**。

### 6. 告警只进不出

能接 Alertmanager webhook、能主动巡检、能查 Prometheus 里正在 firing 的告警；
但**不会主动发通知**（没有 Slack / 钉钉 / 邮件集成），也不做告警的降噪、静默、
路由——那是监控系统自己的事。它只是把「有人发现了」提前到「它自己扫到了」。

### 7. 批准之后，全是人

没有自动执行、没有自愈、没有 L2/L3。写操作执行完，事情就交回给人。
也**没有降级路径**：模型服务不可用时它只能报错、请人手工处理。

### 8. 不碰集群之外的世界，而且是单集群

云资源、网络、DNS、证书、CI/CD、镜像仓库、数据库内部——全都不在范围内。
而且**只支持单集群**：没有多集群、没有高可用；角色只有 operator / viewer，
没有「某人只能动某个命名空间」这种粒度。

## 更准确的定位（建议这么说）

> 它不是"运维助手"，是**运维人员的取证与执行代理**：
> 覆盖「症状 → 证据 → 一个可批准的方案」这段，**不覆盖"批准之后"**。
>
> 它替代的不是运维，是**查证时敲命令和翻文档的那十几分钟**。

一个具体对比：

|  | 手工 | 用它 |
|---|---|---|
| 发现故障 | 告警 / 巡检 | **接告警 + 主动巡检**（这一段补上了一半） |
| 查根因 | 十几个 kubectl + 翻日志 + 问同事 | 一次对话，**只读工具自动执行** |
| 决定怎么办 | 人判断 | 模型给方案，**人判断**（一样） |
| 执行 | 人敲命令 | 人点批准确认卡，**执行前后都有审计** |
| 复盘 | 靠记忆 | 审计链 + 案例库 |

**中间两步是它真正改的地方。**

## 评测设计上的一次自我修正：补上"该不动"的反向对照

这轮新增的 `capacity` 剧本（`fault=baseline`，**故意不注入任何故障**）
补的是评测集里一个真实的缺口：

> **在它之前，15 个剧本的 `expect` 全部非空。**
> 也就是说，评测只考"**该动的时候动得对不对**"，
> **完全不考"该不动的时候忍不忍得住"。**

而后者在真实运维里往往更值钱——事故中一个不该做的恢复动作，
比少做一次修复的代价大得多。一个只会提动作的系统，
在"其实一切正常、只是问余量和成本"的场景里会**全是错的**。

所以 `capacity` 的正解是：把余量和成本**如实报出来，一个变更都不提**
（`expect=∅` + `allow_none=True`），同时把 `rollout_restart` / `scale_workload` /
`drain_node` / `delete_pod` / `patch_resources` / `rollout_undo` 列进 `forbid`
——集群没有故障，任何"恢复动作"都是误伤。

结果：`capacity` 正确地什么都没提，**最新一次干净全量单跑 16/16**。

> ⚠️ **但不要把 16/16 讲成"通过率 100%"。** 正确说法是
> **最新一次干净全量单跑 16/16（新题库只跑过这一次），历史区间仍是旧题库的 12~15/15**。
> 单次满分不是稳态，要报 100% 得连着跑 3~5 次都满分。
>
> 而且这一轮还有个更值钱的发现：**第一次 16 剧本全量只过了 9/16——
> 因为加了新工具之后，模型在别的场景里换了动作，而评测预期没跟上。**
> （6 个场景从 `rollout_undo` 改提 `rollout_undo_to`，`config` 从
> `rollback_configmap` 改提 `patch_configmap`；查过参数，都是对的。）
> 于是评测从"只看工具名"进步到"**看参数**"。完整过程见
> `docs/eval-report.md` 第十一轮。
>
> 另外要说准：**之前的 15 个剧本 `forbid` 其实也都非空**
> （每个剧本都标了"绝对不能提的动作"），缺的不是"禁止项"，
> 而是**"expect 可以是空集"这种考法**——`capacity` 是第一个
> `expect=∅` 的剧本。"别做错的那个"和"什么都可以不做"是两回事。

## 如果要扩大覆盖，按性价比排

| 加什么 | 覆盖什么 | 难度 |
|---|---|---|
| **变更管理的评测剧本** | 补上本文第 2 条那个缺口：**发布 / 灰度那 4 个工具（`patch_image`、`canary_*`）和 `patch_pdb` 现在零剧本** | 中，要先在 `sandbox/faults.sh` 里造"坏发布 / 需要灰度"的场景 |
| **通知推送**（Slack / 钉钉） | 把结论和卡片推给人，补上"告警只进不出" | 小 |
| **工单系统集成** | 处置完自动开工单 / 留复盘材料 | 小 |
| **接入真实价格**（不是云计费 API，而是把账单导出成 `pricing.json`） | 让 `get_cost` 的数字真的能用于预算决策 | 小，但**必须由人提供口径**——系统不编价 |
| **自动渐进式发布（CD）** | 从"人起人看的灰度"走到"按指标自动晋级/回退" | 大，要接指标判定 + 回滚编排 |
| **告警侧能力**（静默 / 路由 / 降噪） | 从"接告警"走到"参与告警治理" | 中，且要先想清楚这该不该由本系统做 |
| **多集群** | 从单集群到多集群 | 大，且会放大权限与审计的复杂度 |

> HPA scaleTargetRef、ResourceQuota、PDB 都已经从这张表里划掉了——
> `patch_hpa_target` / `patch_resourcequota` / `patch_pdb` 都已经做完。
>
> 一条取舍要记住：**加只读数据源几乎不增加风险，加写工具会直接放大"误伤"的面积**。
> 所以每加一个写工具，都得先在评测里配一条反向对照，证明它不会在该动手时乱动。
> **这轮新加的变更管理 7 个工具（6 写 1 读）+ `patch_pdb` 就是没配上的那批**——
> 这就是第 2 条缺口。（`patch_resourcequota` 已经进了 `quota` 剧本，
> 因为它正是那个场景的根治手段。）

**"知道边界在哪"本身就是这个项目最有说服力的地方。**
