# 这套系统覆盖了运维人员多少工作内容

> 面试会问「这能替代运维吗」。**标准答案是：不能，它覆盖的是一段工作流，不是一个岗位。**
> 下面是可以直接拿去答的分解。
>
> ⚠️ 本文按**当前代码**写（`src/omagent/tools.py` / `patrol.py` / `mcp_client.py` /
> `evals.py`）。早先版本曾写「告警巡检基本没有」「写工具只有 10 个」
> 「配置类改不了」——**这三条现在都不成立了**，下文已按现状重写。
> 同一轮里又更新掉两条：「HPA 的 scaleTargetRef 改不了」和「没有任何工具是
> `severe`」——现在前者有 `patch_hpa_target`、后者有解锁出来的 `delete_pvc`。

---

## 一句话

**它覆盖的是「从发现问题 → 到给出一个可批准的方案」这一段。**
按工作量粗算，K8s 运维的日常里它大概沾到 **15%~25%**——但更准确的说法是
**它覆盖了一段工作流，不是工作量的百分比。**

而且它**不减少工作量，它压缩的是"查证"这一步的成本**：
原来要敲十几个 kubectl、翻文档、问同事，现在一次对话。

> 「发现问题」这一段以前是空缺，现在**补上了一半**：
> 能接 Alertmanager 告警、能定时主动巡检，但**只自动触发只读调查**，
> 产出仍然是一张待批卡片（见下）。

---

## 当前能力快照（先看这几个数）

| 维度 | 当前值 |
|---|---|
| 内置只读工具 | **15 个**（`get_*` + `search_cases`），自动执行、不需要批准 |
| 内置写工具 | **15 个**，全部要人工批准 |
| 默认锁着的可解锁动作 | **1 个**：`delete_pvc`（`danger="severe"`，需 `--allow-tool delete_pvc` 显式解锁） |
| 只读 provider 工具 | 最多 **5 个**：Prometheus 3（`query_metrics`/`get_alerts`/`get_targets`）+ Loki 1（`query_logs`）+ 发布历史 1（`get_recent_changes`，默认总开） |
| 外部 MCP 只读工具 | **可显式导入**（默认一个都不导入，必须由人点名白名单） |
| 默认拒绝动作 | **8 个**。其中 **1 个可解锁**（`delete_pvc`）、**3 个永久禁止**（`delete_namespace`/`modify_rbac`/`exec_in_pod`）、**4 个还没安全实现所以解不开** |
| 诊断评测 | 15 个剧本；**最新一次干净全量单跑 15/15**，历史 **12~15/15**（**不要报 100%**）；`crash`+`config` 单跑 2/2 |
| 巡检/告警 | Alertmanager webhook + 主动巡检；**只触发只读调查**，不发通知 |

## 逐项对照

| 运维工作内容 | 占比 | 覆盖度 | 具体 |
|---|---|---|---|
| **监控告警响应 / 巡检** | ~30% | ⚠️ **补上了一半** | 有 Alertmanager webhook（`POST /api/alert`）和主动巡检（`patrol.py`，`--patrol-interval`）：先做**确定性预筛**（零模型成本），只对异常工作负载起调查；同目标有**冷却去重**。但**只自动触发只读调查，产出仍是待批卡片**；不会发通知，也不做告警的降噪/静默/路由 |
| **故障诊断（查根因）** | ~20% | ✅ **最强的一段** | 15 个剧本，**最新一次干净全量单跑 15/15、历史 12~15/15**；15 个内置只读工具 + 最多 5 个只读 provider 工具，**还能接外部 MCP 只读工具**；能自己算「最近改了什么」；可检索 runbook |
| **故障处置** | ~20% | ⚠️ **15 个写工具，且必须人批** | 见下节清单。含后来补上的 **4 个配置类工具**和 **`patch_hpa_target`**；`danger` 只影响卡片摩擦强度，**不是准入分级** |
| **变更管理（发布/回滚/灰度）** | ~15% | ⚠️ **只有回滚** | `rollout_undo` / `rollback_configmap` 可以；**发布不行**（`apply_manifest` 在禁止清单里）；灰度/CD 完全没有 |
| **容量与成本** | ~5% | ❌ 没有 | 能读 ResourceQuota / 资源用量 / HPA 状态，**不能改配额、不能做容量规划、不算钱** |
| **稳定性建设（PDB/探针/配额规范）** | ~5% | ⚠️ **能改一部分了** | 探针端口、nodeSelector、Service selector / targetPort 都能改；**PDB 和 ResourceQuota 改不了** |
| **工单 / 文档 / 交接 / 复盘** | ~5% | ❌ 没有 | 有审批卡片和审计链，但工单系统、文档、复盘报告都没有 |
| **集群生命周期（建集群/升级/节点运维/备份/安全加固）** | — | ❌ **零** | 完全没碰 |

## 能改的 15 个动作

```
# 让现状恢复类
rollout_restart     rollout_undo       scale_workload     delete_pod
patch_resources     patch_hpa          patch_hpa_target   rollback_configmap
cordon_node         uncordon_node      drain_node

# 后来补上的 4 个配置类修复
patch_service_selector   patch_service_port   patch_probe   patch_node_selector
```

那 4 个配置类工具是补上评测里「症状像重启、其实重启没用」那几个陷阱场景的正解。
`patch_hpa_target` 是补上「HPA 的扩缩容目标被改坏」——它的正解从
"我没有工具" 变成了"把 scaleTargetRef 改回去"。
但它们**不是"随便改 YAML"**——能改的字段是枚举出来的（selector、targetPort、
探针端口、nodeSelector 的增删、HPA 的 scaleTargetRef），除此之外表达不了。

**每个写操作都必须人工批准**：一张带影响面、dry-run 结果、回滚方式和
`rationale` 的确认卡片。`danger=caution` 的再加醒目警告；
`danger=severe` 的（当前只有解锁出来的 `delete_pvc`）**必须手输目标名字才能批准**。

> `severe` 档位曾经是"预留但从未被走过"的死分支。现在它**第一次被真实使用并
> 在浏览器里验证过了**（`tests/e2e_frontend.py::test_severe_gate`：卡片头标 severe、
> 危险横幅、手输确认框、未输入禁用、**输错仍然禁用**、输对解锁、改回错的重新锁上）。
> 验证它需要服务用 `--allow-tool delete_pvc` 启动。

## 明确做不到的（这才是重点）

### 1. 不能发布、不能改任意 YAML

`apply_manifest` 在禁止清单里，而且**解不开**（还没有安全实现）。所有写能力都是
**参数化工具**——「改一段任意 YAML」这件事**根本表达不了**。所以镜像变更、
灰度发布、CD 都不在范围内，只能靠回滚退回去。

### 2. HPA 的 scaleTargetRef —— **现在能修了**（这条以前是"做不到"）

以前 `patch_hpa` 只能改 `minReplicas` / `maxReplicas`，改不了 `scaleTargetRef`，
所以 `hpa` 场景的正解是"我没有工具"。**现在补上了 `patch_hpa_target`**：
整块替换 `scaleTargetRef`，评测里 `hpa` 的 `expect` 从 `∅` 变成 `{patch_hpa_target}`，
同时把 `patch_hpa` 设成**陷阱**（目标指错时改副本区间治不了，属于"看着在处置、
其实什么也没修"）。

> 也就是说：**"15 个剧本里唯一一个正解=明说没工具的场景"这句话已经不成立了。**
> 当年属于这一类的 `selector` / `port` / `probe` / `pending` 也都已有了参数化工具。
> 真正"只能明说没工具"的，现在只剩禁止清单里的动作。

### 3. 默认不做危险动作（8 个默认拒绝，其中 1 个可显式解锁）

```
delete_workload   delete_namespace   delete_pvc   delete_pv
modify_rbac       read_secret        exec_in_pod  apply_manifest
```

这 8 个**默认根本不出现在模型可见的工具清单里**。但要分清三种状态：

| 状态 | 有哪些 | 说明 |
|---|---|---|
| **可显式解锁** | `delete_pvc` | 启动时 `--allow-tool delete_pvc`，解锁后仍要审批，且 `severe` 手输名字 |
| **永久禁止** | `delete_namespace`、`modify_rbac`、`exec_in_pod` | 任何参数都打不开——它们破坏的是**架构前提**（提权 / 破边界） |
| **还没有安全实现** | `apply_manifest`、`delete_pv`、`delete_workload`、`read_secret` | 仍在禁止清单里，现在也解不开——因为还没写出可审的实现 |

`modify_rbac` 是提权路径，`read_secret` 会碰凭据，`exec_in_pod` 等于把集群交出去，
`apply_manifest` 是「参数化之外的口子一律不开」。
**解锁 `delete_pvc` 不等于 dry-run 能兜住它**：服务端对删除的 dry-run
**不校验任何后果**（实测：删一个正在被 Pod 使用的 PVC，`--dry-run=server`
照样返回成功），所以它的安全边界是「默认锁着 + severe 手输名字 + 审计」，
**不是 dry-run**。

### 4. 告警只进不出

能接 Alertmanager webhook、能主动巡检、能查 Prometheus 里正在 firing 的告警；
但**不会主动发通知**（没有 Slack / 钉钉 / 邮件集成），也不做告警的降噪、静默、
路由——那是监控系统自己的事。它只是把「有人发现了」提前到「它自己扫到了」。

### 5. 批准之后，全是人

没有自动执行、没有自愈、没有 L2/L3。写操作执行完，事情就交回给人。
也**没有降级路径**：模型服务不可用时它只能报错、请人手工处理。

### 6. 不碰集群之外的世界，而且是单集群

云资源、网络、DNS、证书、CI/CD、镜像仓库、数据库内部——全都不在范围内。
而且**只支持单集群**：没有多集群、没有高可用；角色只有 operator / viewer，
没有「某人只能动某个命名空间」这种粒度。

## 更准确的定位（建议这么说）

> 它不是"运维助手"，是**运维人员的取证与执行代理**：
> 覆盖「症状 → 证据 → 一个可批准的方案」这段，**不覆盖"批准之后"**。
>
> 它替代的不是运维，是**查证时敲命令和翻文档的那十几分钟**。

一个具体对比：

|  | 手工 | 用它 |
|---|---|---|
| 发现故障 | 告警 / 巡检 | **接告警 + 主动巡检**（这一段补上了一半） |
| 查根因 | 十几个 kubectl + 翻日志 + 问同事 | 一次对话，**只读工具自动执行** |
| 决定怎么办 | 人判断 | 模型给方案，**人判断**（一样） |
| 执行 | 人敲命令 | 人点批准确认卡，**执行前后都有审计** |
| 复盘 | 靠记忆 | 审计链 + 案例库 |

**中间两步是它真正改的地方。**

## 如果要扩大覆盖，按性价比排

| 加什么 | 覆盖什么 | 难度 |
|---|---|---|
| **通知推送**（Slack / 钉钉） | 把结论和卡片推给人，补上"告警只进不出" | 小 |
| **工单系统集成** | 处置完自动开工单 / 留复盘材料 | 小 |
| **更多参数化写工具**（ResourceQuota、PDB） | 把剩下"只能明说没工具"的场景补掉 | 中，每个都要能过 dry-run |
| **告警侧能力**（静默 / 路由 / 降噪） | 从"接告警"走到"参与告警治理" | 中，且要先想清楚这该不该由本系统做 |
| **多集群** | 从单集群到多集群 | 大，且会放大权限与审计的复杂度 |

> HPA scaleTargetRef 已经从这张表里划掉了——`patch_hpa_target` 已经做完并进了评测。
>
> 一条取舍要记住：**加只读数据源几乎不增加风险，加写工具会直接放大"误伤"的面积**。
> 所以每加一个写工具，都得先在评测里配一条反向对照，证明它不会在该动手时乱动。

## ⚠️ 面试时绝对不要说的

| 别说 | 为什么 |
|---|---|
| "能替代运维" | 上面那张表摆着呢，一问就穿 |
| "覆盖运维 80% 的工作" | 差得远，而且这个数字编不出来 |
| "生产级" | 单集群 demo，社区为 0 |
| "通过率 100%" | 最新一次干净全量单跑确实是 15/15，但历史区间是 12~15/15——**单次满分不是稳态**。要报 100%，得连着跑 3~5 次都满分 |
| "所有危险动作都能解锁" | 只有 `delete_pvc` 一个；另外 3 个永久禁止、4 个还没实现 |

**要说的是**：它把一段工作流做扎实了（诊断**最新 15/15、历史 12~15/15**），
而且**清楚地知道自己不该做什么**——8 个默认拒绝动作（1 个可显式解锁、3 个永久禁止、
4 个还没实现）、写操作必须人批、巡检只触发只读调查、扩展数据源不能削弱安全边界。
**"知道边界在哪"本身就是这个项目最有说服力的地方。**
