# Agent 开发：能力地图与学习路径

> 面向：想转 Agent 开发的人 ｜ 标注了「**你已碰过**」的部分——
> 你在 K8s 运维 Agent 那个项目里已经实操过相当一部分，先看清自己站在哪。

---

## 0. 先纠正一个普遍误解

大多数人以为 Agent 开发 = **调模型 + 写提示词**。

实际上那只是第一层。真正决定成败的是后面几层：

```
① LLM 能力          ← 大多数人只学这层
② 工具设计          ← Agent 与"聊天机器人"的分界线
③ 上下文工程        ← 决定上限
④ 评测              ← 最被低估，最能拉开差距
⑤ 可靠性与安全      ← 决定能不能上生产
⑥ 领域判断          ← 决定你做的 Agent 有没有用
```

**一句话**：Agent 开发的核心不是"让模型更聪明"，
而是"**在模型不可靠的前提下，把系统做可靠**"。

---

## ① LLM 能力层：必须懂，但不用深

你不需要会训练模型，但要理解它的**行为边界**。

| 概念 | 为什么必须懂 |
|---|---|
| **Token / 上下文窗口** | 成本和"记不住"的根源。一个"字"≈1-2 token，中文更贵 |
| **采样参数**（temperature / top_p / max_tokens） | `temperature=0` 是"尽量选概率最高的"，**不是确定性** |
| **结构化输出**（JSON mode / function calling） | Agent 的地基：让模型输出**能被程序解析**的东西 |
| **幻觉** | 模型会一本正经地编。**必须假设它一定会编**，用结构去防 |
| **成本模型** | 输入/输出分别计价，输出通常贵 3-4 倍 |
| **流式输出** | 体验问题：等待 20 秒和"逐字蹦出来"感受完全不同 |
| **工具调用格式** | 模型如何"说"要调用哪个工具、带什么参数 |

### 两个反直觉的点

**① `temperature=0` 不保证可复现。**
托管推理的**连续批处理**和 **MoE 路由**会带来输出漂移。
你在项目里实测过：**被测系统与 harness 完全相同的两次跑分，差了 7.4 个百分点**
（54.4% vs 61.8%）。

> ⚠️ 讲这个数字时要小心：**必须先确认两次跑分用的是同一版代码**。
> 你项目里一开始没做这件事，差点把"harness 改动的影响"当成"模型方差"——
> 后来加了**代码指纹**（记录 SUT/harness/用例集的哈希），跑分才能归属到版本。

> **推论**：任何"跑一次得一个数"的评测都不可信。

**② `max_tokens` 包含思考过程。**
如果用带推理的模型，reasoning token 会吃掉配额，导致返回**空内容**。
你踩过这个坑：早期 LLM 返回空串，排查发现 `max_tokens` 全被 reasoning 消耗了。

> **你已碰过**：采样参数、结构化输出、幻觉防护、成本计量、空返回排查。

## ② 工具设计层：Agent 的分界线

**这是 Agent 和聊天机器人的真正区别**，也是最容易被做砸的一层。

### 核心原则

**① 参数化，不要自由命令**

| ❌ 坏设计 | ✅ 好设计 |
|---|---|
| `run_shell(command="kubectl delete pod x")` | `delete_pod(namespace, name)` |
| `query(sql="任意 SQL")` | `get_order(order_id)` |

**为什么**：自由命令让模型有一次"自由发挥"的机会，
而每一次自由发挥都是幻觉变成事故的入口。
参数化把模型的输出空间**收窄到你能校验的范围**。

**② 工具描述就是提示词**
模型只能通过 `name` + `description` + `参数 schema` 理解工具。
描述写得含糊，模型就会用错——**这不是模型的问题，是你的问题**。

**③ 工具的返回值也要设计**
返回一大坨 JSON 还是精炼的文本？**这直接决定模型的判断质量**。
你的项目里，工具返回的是人可读文本（`pod phase=Running ready=true restarts=3`），
而不是原始对象——因为模型读文本比读嵌套 JSON 更准。

**④ 至少标出"这个工具有副作用吗"**
只读工具可以自动执行；写工具需要门禁。**这个切分必须是固定的、写在代码里的**，
不能让模型自己判断。

### 最容易被忽视的：工具的可靠性

> **工具一崩，模型只会说"证据不足"——而你会以为是模型太笨。**

你在项目里踩的就是这个：测试替身缺了两个字段，导致 `get_workload` 整条抛异常。
**68 条用例里 33 条受影响，LLM 的分数被压低了一半**，
而排查前你一直以为"是模型不行"。

> **教训**：替身/桩必须与真实接口**同构**，否则你测的是替身，不是产品。

> **你已碰过**：参数化工具、工具描述、返回值设计、只读/写切分、工具故障排查。

## ③ 上下文工程层：决定上限

现在业界越来越认同：**Agent 的质量上限由上下文质量决定，不是由模型决定。**

### 要懂什么

| 概念 | 说明 |
|---|---|
| **上下文的结构** | system / 工具描述 / 历史 / 检索结果 / 当前输入——每部分都在抢窗口 |
| **上下文压缩** | 对话长了必须摘要，否则爆窗口 |
| **检索增强（RAG）** | 把知识库塞进上下文的工程 |
| **记忆分层** | 短期（本次对话）/ 长期（跨会话知识沉淀） |
| **少样本示例** | 给 2-3 个"输入→正确输出"的例子，效果常胜过一页说明 |
| **什么时候不该塞东西** | **上下文不是越多越好**——无关内容会稀释注意力 |

### 一个具体技巧

**"给模型看事实，不要给模型看你的结论"。**
你的项目里，喂给 LLM 的是原始事实（Pod 状态、事件、日志），
而不是规则引擎的判断——**否则它会懒，直接抄你的结论**。

> **你已碰过**：上下文结构、知识沉淀（症状→根因→处置→结果四元组）、相似检索。

## ④ 评测层：**最被低估，最能拉开差距**

如果说只能精通一层，**选这层**。

### 为什么它最重要

在传统开发里，代码写对了就是对了。
在 Agent 开发里，**"对"是需要被测量的**——而且测量方法本身很容易骗自己。

### 要懂什么

| 概念 | 说明 |
|---|---|
| **用例集设计** | 每条用例要包含"输入 + 期望 + **绝对不能做的事**" |
| **确定性 vs 非确定性** | 规则是确定的，LLM 不是。**方差必须被测量和报告** |
| **多次运行** | LLM 评测至少跑 3 次报区间，不要报单点 |
| **假阳性 vs 漏报** | 在多数领域，**假阳性危害更大**（主动造成伤害） |
| **LLM-as-judge 的陷阱** | 用模型打分很方便，但**要把 judge 本身也验证一遍** |
| **离线回放** | 把真实调用录下来，离线重放——快、便宜、可进 CI |
| **回归护栏** | 把"绝不能发生的事"做成构建门禁（如"危险动作提议数必须为 0"） |
| **自证问题** | **自己出的题自己考**——必须引入外部数据或独立出题人 |

### 三个你在项目里已经历过的教训

1. **评测工具本身会有 bug** —— 你的替身有 3 个保真度 bug，
   把 LLM 分数压低了一半。**评测需要被验证。**
2. **同一配置跑两次结果不同** —— 54.4% vs 61.8%。
   **不报单一数字，报区间。**
3. **评分口径会偷偷奖励错误行为** —— 你的口径奖励"猜中标签"、惩罚"证据不足时拒绝动手"，
   而在运维里**拒绝动手往往是对的**。

> **面试高频问题**："你怎么知道你的 Agent 做对了？"
> 能把这三条讲清楚，就超过了大部分候选人。

> **你已碰过**：用例集、CI 护栏、离线回放、真实数据对比、方差测量、自证问题的应对。

## ⑤ 可靠性与安全层：决定能不能上生产

### 可靠性

| 要懂 | 说明 |
|---|---|
| **重试与退避** | 模型 API 会超时、会 5xx。指数退避 + 上限 |
| **降级路径** | 模型不可用时怎么办？**你的项目里是降级到规则引擎** |
| **超时** | 每一层都要有，否则一个卡住的工具会拖死整个请求 |
| **幂等** | 重试不会造成二次副作用 |
| **可观测性** | 每一步都要能 trace：调了什么工具、返回什么、花了多少 token |
| **成本与延迟控制** | 缓存、批处理、小模型分流 |

### 安全（Agent 特有，和传统 Web 安全不同）

| 风险 | 说明 | 防护 |
|---|---|---|
| **Prompt Injection** | **最危险**。工具返回的内容里可能藏指令（比如网页、日志、文件里写着"忽略之前的指示"） | 把工具返回值当**数据**不当指令；权限最小化 |
| **越权操作** | 模型提议了不该做的动作 | 白名单 + 危险动作分级 |
| **凭证泄漏** | 模型把密钥写进输出 | 脱敏；不把密钥放进上下文 |
| **不可逆操作** | 删数据、删资源 | 分级禁做 / 强确认 / dry-run |
| **审计缺失** | 出事了查不到 | 全链路留痕，且**防篡改** |

### 一个核心设计思想

> **安全必须由结构保证，不能靠提示词。**
> 提示词可以被注入、被越狱；`if` 语句不行。

你在项目里的三条不变量就是这个思路的范例：
工具级固定切分、方案生成与执行分离、批准凭证与方案强绑定。

> **你已碰过**：降级、幂等、dry-run、危险动作分级、审计链、结构性安全。

## ⑥ 领域判断层：决定有没有用

**Agent 不是通用能力，是"通用推理 + 某个领域的工具 + 那个领域的判断"。**

一个 Agent 好不好用，往往取决于：

- 你选的**工具**是否覆盖了这个领域的真实操作
- 你定义的**"做对了"**是否符合这个领域的标准
- 你知道这个领域**哪些操作是绝对不能碰的**

> 你在 K8s 运维领域已经有了这些：五层根因、归因优先级、变更风险控制。
> **这就是你的差异化**——纯做 Agent 框架的人做不出这个。

**建议**：选一个你**真的懂**的领域做 Agent，而不是做"通用 Agent"。

## 优先级：如果只有 3 个月

| 周 | 学什么 | 怎么练 |
|---|---|---|
| 1–2 | LLM 基础 + 结构化输出 | 写一个"调用模型 → 拿到结构化 JSON → 校验"的最小程序 |
| 3–4 | **工具调用循环** | 做一个只有 3 个只读工具的 Agent，能多轮查证 |
| 5–6 | **上下文工程** | 给上面那个 Agent 加记忆和检索 |
| 7–9 | **评测** | 写 20 条用例，跑通"离线回放 + CI 护栏" |
| 10–11 | 可靠性 + 安全 | 加重试/降级/超时；加一道"危险动作门禁" |
| 12 | 收尾 | 把方差测出来，写成报告 |

**关键**：**第 7-9 周的评测不要跳过。**
大多数人卡在第 4 周就以为学完了，然后在真实项目里无法回答"它到底行不行"。

## 什么是噪音（不必追）

| 噪音 | 真相 |
|---|---|
| **框架崇拜**（LangChain 等） | 框架帮你省的是"接线"的力气。**核心概念不懂，框架只会让你更糊涂**。先手写一遍再考虑框架 |
| **Multi-Agent 万能论** | 大多数场景**一个 Agent + 好工具**就够了。多 Agent 主要增加调试难度 |
| **微调** | 90% 的场景不需要。**先优化提示词、工具和上下文** |
| **追新模型** | 模型三个月换一代。**评测体系和方法论才是你积累下来的资产** |
| **"自主 Agent"** | 全自主在多数业务场景不可接受（责任、合规）。**L1/L2 的 Human-in-the-loop 才是主流** |

## 面试会问什么

**基础**
1. Agent 和聊天机器人的区别是什么？（→ 工具调用）
2. 你怎么防止模型做危险操作？（→ 结构性约束，不是提示词）
3. `temperature=0` 能保证结果一致吗？（→ **不能**，说出原因）

**进阶**
4. 你怎么评测一个 Agent？（→ 用例集 + 方差 + 外部数据 + 假阳性/漏报）
5. 工具调用失败了怎么办？（→ 重试/降级/**别让模型把工具故障当成"证据不足"**）
6. Prompt Injection 怎么防？（→ 数据/指令分离、权限最小化）

**送分（能答出来就赢了）**
7. **你踩过什么坑？**
   → 讲"评测工具自己有 bug，把分数压低了一半"这个故事。
   **它同时证明了你做过、你会测量、你有诚实。**

## 最后

**这个领域还很年轻**，"懂什么"的共识还在形成。
但有一条已经很清楚：

> **能把 Agent 做可靠、能被评测、能说清哪里不行的人，比能写出花哨 demo 的人稀缺得多。**

你那个项目虽然有不少缺陷，但它**踩过的坑和建立的评测纪律**，
比一个"一次跑通、数字漂亮"的 demo 更能证明你的能力。

**下一步建议**：把第 ④ 层（评测）作为主攻方向。
它是目前最缺人、最难被替代、也最不依赖追新的一层。
