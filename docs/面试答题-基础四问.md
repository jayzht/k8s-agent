# 面试答题：基础四问

> 这是《简历素材》里「基础题」的完整答案。
> 每题的结构：**先给一句话结论** → 展开理由 → **加分点**（拉开差距的地方）→ 可能被追问的方向。
>
> ⚠️ 背答案没用。**每一句你都要能对应到代码或数据**，否则追问一层就露馅。

---

## Q1. 你说的 L1 是什么？为什么不做全自动？

### 一句话结论

L1 = **只读诊断自动执行，所有写操作必须人工确认**。
不做全自动的原因不是技术不行，是——**瓶颈在信任和责任，不在能力**。

### 展开

业界把 AI 的自主权分档：

| 档位 | 能力 | 风险 |
|---|---|---|
| L0 | 只回答，不碰系统 | 最安全，价值也最低 |
| **L1** | **只读自动 + 写操作人工确认** ← 本项目 | 可控 |
| L2 | 低危自动执行，高危审批 | 依赖可靠的"危险分级" |
| L3 | 全自动闭环 | 出事谁负责？ |

停在 L1 的三个理由：

**① 行业现实**：调研显示 **98% 的企业只接受"有条件地让 AI 改生产"，
仅 8.5% 接受全自动关单**。做 L3 等于主动放弃九成市场。

**② 责任无法转移**：变更出事必须有人负责，而 AI 不能承担责任。
所以"要不要人确认"**不是技术问题，是责任问题**。

**③ 实测数据也不支持**：同一套 68 条用例，规则引擎**确定性 100%**，
而 LLM 的跑分**有方差**——同一版代码两次跑分 54.4% vs 61.8%（见下）。
让一个跑分都不稳定的东西自动改生产，风险不可控。

### 加分点 ⭐

> L1 档位下，产品力**不在"多自主"，而在"能不能把一次变更讲清楚，
> 让人 30 秒内敢点确认"**。所以我把力气花在**确认卡片**上——
> 影响面、dry-run、回滚路径、熔断检查一屏说清。
> **确认卡片才是产品，Agent 只是取证工具。**

### 可能被追问

**"那 Agent 的价值在哪？"**
→ 价值在**把 15 分钟的排查压缩到 30 秒**，不是"替人做决定"。
MTTR 的瓶颈通常不是"没人会修"，而是"要花很久才知道发生了什么"。

**"什么情况下你会升到 L2？"**
→ 当①危险分级足够可靠 ②有真实数据证明自动执行的事故率低于人工 ③组织愿意承担剩余风险。
**目前一条都不满足。**

## Q2. 三条安全不变量是什么？怎么保证不被绕过？

### 一句话结论

**工具级固定审批切分、方案生成与执行分离、审批凭证与方案强绑定。**
核心是：**靠代码结构保证，不靠提示词约束模型自觉。**

### 逐条展开

#### 不变量 1：工具级固定审批切分

每个工具在代码里**声明**自己是否写操作：

```python
"rollout_restart": ToolSpec("rollout_restart", True,  ...)   # 写
"get_pods":        ToolSpec("get_pods",        False, ...)   # 只读
```

启动时与 `config/policy.yaml` 的 Tier 定义**交叉校验**，不一致就**拒绝启动**。

> **为什么要这样**：模型**没有机会自己判断**"这个动作安不安全"。
> 切分是固定的、写死在代码里的，模型只能在既定切分下工作。
> 交叉校验是为了防"改了代码忘了改策略"导致的静默漂移。

#### 不变量 2：propose 永不写

生成方案和执行是**两段代码**。`propose()` 只做三件事：
**影响面分析、服务端 dry-run、熔断评估**——全程不产生任何副作用。

> **为什么重要**：即使模型被提示注入攻击、被越狱，
> 它也只能"提议"，**物理上碰不到集群**。

#### 不变量 3：execute 必须批准

`execute()` 需要传入一个 `approved=True` 且 **`proposal_id` 严格匹配**的凭证：

```python
if decision.proposal_id != prop.proposal_id:
    raise GateViolation(
        f"批准凭证与方案不匹配: 期望 {prop.proposal_id}，实际 {decision.proposal_id}"
    )
```

> **为什么重要**：**批准 A 却执行 B 会被拦下**。
> 凭证和方案是绑定的，不能挪用、不能张冠李戴。

### 加分点 ⭐

> 这三条的共同点是：**不是靠"要求模型自觉"，而是代码结构上做不到。**
> 提示词可以被注入、被越狱、被绕过；`if` 语句不行。
>
> 用 **25 条对抗测试**固定这些性质，覆盖：
> 伪造批准凭证、批准 A 执行 B、不批准直接执行、审批后篡改参数、
> 绕过门禁、篡改审计日志、重启绕过冷却期。
>
> 一个真实例子：从 Web 层伪造 `diagnosis_id`/`proposal_id` 直接调执行接口 → **HTTP 409 拒绝**。

### 可能被追问

**"工具白名单本身会不会被绕过？"**
→ 所有工具都是**参数化 schema**，不接受自由命令字符串。
模型只能填参数（如 `replicas=3`），**不能拼 kubectl 命令**。
这是切断"幻觉变成事故"最短路径的地方。

**"如果模型被诱导提出了 T3 动作呢？"**
→ 提议阶段就会**丢弃**（不在白名单里的动作进不了候选集）；
即使硬塞进执行接口，T3 在策略层就是 `executable: false`，**谁批准都没用**。

## Q3. dry-run 解决了什么问题？

### 一句话结论

**让"注定失败的操作"根本到不了人面前。**

### 机制

K8s 原生的**服务端** dry-run（`dry_run="All"`）：
把变更请求发给 API Server，它**完整跑一遍校验**——
schema、准入控制器、admission webhook、RBAC、资源配额——但**不持久化任何东西**。

### 解决两个问题

**① 过滤注定失败的操作**
配额满了你还想扩容？dry-run 直接告诉你不行，**根本不生成可执行方案**。
不让人去点一个必然失败的操作。

**② 校验"本地模拟不出来的东西"**
有些错误只有 API Server 知道——准入 webhook 拒绝、PDB 冲突、字段互斥。
本地怎么写都模拟不全。

### 加分点 ⭐

> 我把它叫做"**免费的 K8s 红利**"：
> 校验用的是**集群的真实规则**，包括集群管理员配的准入策略和 webhook，
> 比我在应用层自己写的校验更权威，而且**不用维护**。

### 主动说局限（这也是加分项）

> dry-run **只校验"能不能提交"，不校验"该不该做"**。
> 配额够、语法对，dry-run 就通过——但它仍然可能是个**业务上错误的决定**
> （比如业务上不该重启）。
> 所以它**不能替代影响面分析和人工确认**，只是把"技术性失败"提前拦掉。

## Q4. 你怎么保证评测不是"自己出题自己考"？

### 一句话结论

**先承认它确实是自证的**，然后引入**外部出题人**。

### 第一步：承认问题

68 条用例是我自己写的，规则引擎在上面 100% 通过——
**这本质上就是自己出题自己考**。不先承认这一点，后面全是自我安慰。

### 第二步：引入两个外部出题人

| 来源 | 做法 | 结果 |
|---|---|---|
| **大模型生成对抗场景** | 提示词明确要求"**在已知分类之外出题**" | 三轮 18 个场景 → **6 假阳性 + 4 漏报 + 2 未识别** |
| **真实事故数据**（IBM ITBench-Lite） | 35 个真实 K8s 事故场景，带人工标注的根因真值 | 3 个落在能力范围内，**实测 3/3 命中** |

### 第三步：防止"拿模型的答案判规则的卷"

生成的用例存在 `evals/generated/`，标注「**待人工复核**」，
**绝不自动加进主用例集**。

> 否则就变成"让模型当裁判"——只是换了一种自证方式而已。

### 第四步：实证——自证确实掩盖过缺陷

最硬的证据是 `probe-003` 这条用例：
它的期望值是**照着当时错误的实现行为写的**。
规则引擎跑它是"通过"的——因为它和自己一致。
**没有外部出题人，这个错误永远发现不了。**

### 加分点 ⭐⭐（最能体现诚实和专业）

> 真实数据还暴露了一个**自造用例永远发现不了的问题**：
> **我的能力范围和真实故障分布严重不匹配。**
> ITBench 里根因分布是 ConfigMap 12、Chaos 注入 11、Pod 3、Deployment 2，
> 而最初我只做了 Pod 状态层。
>
> 也就是说——**自造用例不仅能自证，还会让我在一条越来越窄的赛道上刷分。**
> 后来我把能力从一层扩到五层，正是被这组真实数据逼出来的。

### 可能被追问

**"那 68/68 还有意义吗？"**
→ 有意义，但它的意义是**回归防护**，不是**能力证明**。
它保证"修好的东西不退化"，不能证明"我什么都能修"。
**能力证明必须靠外部数据。**

**"LLM 到底多少分？"**
→ **我不会给单一数字**，因为它跑分有方差：
**被测系统和 harness 都完全相同的两次跑分是 54.4% vs 61.8%**（差 7.4 个点）。
而规则引擎每次都是 68/68——**确定性本身就是一项优势**。

> 这里有个我自己的教训值得说：我最初把**跨越 3 个不同 harness 版本**的四次跑分
> 说成"同一 harness 四次落在 54%–90%"——**这是错的**，
> 把一个 36 点的"伪方差"当成模型波动。后来我加了**代码指纹**
> （每次评测记录 SUT / harness / 用例集的哈希），跑分才能归属到版本。

更关键的是：我原本的数字（55.9%）**是假的**——排查发现我的测试替身有 3 个保真度 bug，
把 LLM 的分数压低了一半（受影响的用例从 33/68 降到 0）。
**这件事让我意识到评测本身也需要被验证。**

还有一个必须说的：剩余失败里**大部分是 LLM 拒绝在证据不足时动手**，
而我的评分口径**奖励"猜中我的标签"、惩罚"谨慎"**——这本身是需要修的设计缺陷。

## 汇总：答得好的标准

| 题 | 及格（能说清是什么） | 优秀（能说清为什么 + 有细节） |
|---|---|---|
| L1 | 说清 L1 定义 | 指出瓶颈在信任和责任；引用 98%/8.5% 调研；**"确认卡片才是产品"** |
| 三不变量 | 说出三条 | **"靠结构不靠提示词"**；举 409 拒绝的具体例子；提到 25 条对抗测试 |
| dry-run | 说清是服务端干跑 | **主动说局限**："只校验能不能提交，不校验该不该做" |
| 评测不自证 | 承认自证 | 给出**两个外部出题人 + 一个实证**（probe-003 期望值写错） |

**贯穿四题的一条主线**：
> **这个项目的价值不在于"AI 多能干"，而在于"想清楚了 AI 不可靠时系统怎么办"。**
