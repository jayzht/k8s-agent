## 项目经历

### K8s 运维 Agent —— 对话式集群诊断与受控变更　｜　个人项目　｜　2026.09

`Python` `Function Calling` `MCP` `Kubernetes` `Docker` `确定性评测`
　`github.com/jayzht/k8s-agent`

> 运维人员描述症状，Agent 调工具取证并给出结论；**只读查询自动执行，
> 改动集群必须先出一张人来批的确认卡片**。

- **安全执行架构（核心设计）**：内置 15 只读 + 10 写工具，**未登记的工具一律
  判定为写操作并拒绝**（fail closed）。写路径必须携带与方案绑定的批准凭据
  （批准 A 无法执行 B），执行前**重跑一次服务端 dry-run** 防止审批期间的集群漂移，
  叠加命名空间白名单、方案 TTL 与哈希链审计。
- **提示注入防御**：把集群里读到的日志/事件当作**不可信输入**——围栏标注 +
  加权信号计分，**只标注不删改原文**（清洗掉等于销毁证据）；命中即发事件、写审计、
  控制台弹告警卡。调研 8 个同类开源项目后确认：**无一个实现该能力**。
- **工具层可拔插**：`Provider` 协议 + 注册表，**拒绝缺少 dry-run 契约的写工具**
  （扩展能力不削弱安全边界）；自带只读 Prometheus / Loki；实现 **MCP 双向**——
  既是 MCP server（只借出只读能力），也是 MCP client（接外部工具，
  **对端自称只读不算数，必须人工点名**）；支持在 Web 页面上直接添加外部工具并热生效。
- **评测驱动的迭代（最有含金量）**：15 个真故障剧本、真集群真模型、
  **确定性判据（不用 LLM 当裁判）**。先用重复采样把「抽样波动」和「可复现缺陷」
  分开，再逐个定位修复，**把 10~11/15 提到 14/15（93%）**，
  且每一步都有前后对照的评测记录。抗注入 1/1。
  过程中两次假设被评测直接证伪（"加个工具就行" → 实测 15 个场景调用 0 次）。
- **工程质量**：284 条单元测试 + 31 项前端端到端；容器化交付（Docker + Compose +
  一条命令从零建集群）；`doctor` 自检逐项检查 RBAC / metrics-server / 模型配置
  并给出可粘贴的修复命令。

# 学习路线（按"对求职的边际收益"排序）

> 每条都写了**拿什么证明学会了**——没有产出物的学习，简历上写不了。

## P0：LangChain / LangGraph（1~2 周）

**为什么最优先**：JD 出现率最高，而你正好可以用**对比**的方式学。

**怎么做**：用 LangGraph 把本项目的 agent loop 重写一遍（工具调用 → 审批中断 →
恢复执行）。LangGraph 的 `interrupt` 机制和你的审批卡是同一个问题。

**产出物**：一篇对比笔记 + 代码。简历上写
「**手写 agent loop 与 LangGraph 两种实现对比**」，面试时直接回答"你为什么不用框架"。

## P1：RAG + 向量库（1~2 周）

**为什么**：第二高频关键词，而且是**独立可展示**的能力。

**怎么做**：给这个项目加一个 RAG 入口——把 K8s 官方文档 / runbook 做成可检索的
知识库，让 Agent 在给处置建议前先查文档。**和现有 runbook 机制对比**：
结构化签名检索 vs 向量召回，各自适合什么。

**产出物**：能跑的最小 demo + 一段"A/B 对比"的结论。这比"我会 RAG"强得多。

## P2：可观测性 tracing（3~5 天）

**怎么做**：给现有循环加 span——每次 LLM 调用的 token/耗时、每次工具调用的延迟，
聚合成 trace。你已经有 `trace_id` 和审计链了，接 OpenTelemetry 是顺手的事。

**产出物**：一张 trace 截图放进 README。

## P3：SSE 流式输出（2~3 天）

**怎么做**：现在前端是轮询（`/api/poll`），改成 SSE 推送。你已经有事件流了，
只是换个传输方式。

**产出物**：前端首字延迟的对比数字。

## 不建议现在花时间的

- **微调（LoRA/SFT）**：应用岗基本不问，投入产出比低
- **推理部署（vLLM）**：偏平台岗，等你确定方向再说
- **多 Agent 协作**：除非目标 JD 明确提到，否则"能讲清楚什么时候不该用多 Agent"更值钱
