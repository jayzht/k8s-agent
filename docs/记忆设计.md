# 记忆为什么这样做，优势在哪

> 面试高频问题。**答案的重点不在"我选了结构化"，在"我知道它的代价是什么"。**

---

## 一句话

**我没有做"向量记忆"，做的是「可验证的结构化案例库」——
只学执行后复查确认有效的修复，而且检索过程完全可解释、可审计。**

在这个项目里，**"可信"比"能记住"重要得多**——因为它要让人批准一次集群变更。

---

## 设计是什么（四层）

### 1. 症状签名：确定性计算，不是 embedding

```python
symptom_tokens(k8s, ns, kind, name)  # → ['pending', 'replicas_short', 'unhealthy', ...]
```

从集群**算**出来的一组稳定词：Pod 状态、退出码、重启次数、就绪情况、
事件原因、Endpoints 就绪数、targetPort 交叉比对、HPA 目标、调度约束……

**关键：两次故障是不是"同一类"，在这里是确定性判断，不是相似度猜测。**

### 2. 检索：Jaccard 相似度 + 阈值

**Jaccard 相似度 = 两个集合的交集大小 ÷ 并集大小**，取值 0~1：

```python
len(sa & sb) / len(sa | sb)
```

用集合而不是向量，是因为**症状 token 没有顺序、也不该重复计数**——
"有 pending 也有 crashloop"和"有 crashloop 也有 pending"是同一件事。

本项目的真实数值（用 `cordon/pending/oom/config` 的实际签名算）：

| 对比 | 交集 | 并集 | Jaccard | 是否命中（≥0.5） |
|---|---|---|---|---|
| cordon vs cordon | 4 | 4 | **1.00** | ✓ |
| cordon vs pending | 3 | 5 | **0.60** | ⚠️ **✓（这是问题）** |
| oom vs config | 3 | 7 | 0.43 | ✗ |
| pending vs config | 2 | 7 | 0.29 | ✗ |

`search(tokens, min_score=0.5)` 里的 0.5 就是**闸门**：低于它直接不返回。
代码里的原话：**「宁可返回空，也不要给一条不相关的经验。」**

### ⚠️ 阈值这条路我实测走不通（重要）

有人会问：那把阈值调到 0.7 不就安全了？**我试了，没用。** 真实数据：

| 当前场景 | 对照案例 | 它推荐 | 原始相似度 | 该不该匹配 |
|---|---|---|---|---|
| `config` | api-gateway 案例 | `rollout_undo` ❌ | **0.80** | 不该 |
| `config` | cart-service 案例 | `patch_resources` ❌ | **0.71** | 不该 |
| `oom` | cart-service 案例 | `patch_resources` ✅ | **0.71** | **该** |

**看最后两行：该匹配的和不该匹配的，原始相似度完全一样（都是 0.71）。**
阈值再高也分不开——调高会连正确的经验一起筛掉，调低就放进错的。

**根因是"通用词"在稀释信号**：`replicas_short` / `unhealthy` /
`partial_endpoints` / `not_ready` 这些几乎每个故障都有，它们贡献了大部分交集，
于是不相干的故障也能拿到 0.7~0.8。

**把通用词剔掉再算，立刻分开**（同一份数据）：

| 对比 | 原始 | 剔通用词后 |
|---|---|---|
| `config` vs api-gateway 案例 | 0.80 | **0.00** ✅ 正确排除 |
| `config` vs cart-service 案例 | 0.71 | **0.33** ✅ 正确排除 |
| `oom` vs cart-service 案例 | 0.71 | **1.00** ✅ 正确命中 |

**所以正确的修法是「按 token 的区分度加权」（类似 IDF：出现得越普遍、权重越低），
不是调阈值。** 阈值管不了这件事——**信号根本不在那个数里。**

> 这一步我先按 0.7 止血（能挡住 0.57 那一类），但**真正的修是加权**。
> 而且这次教训很直接：**我一开始看到的"1.00 vs 0.57 中间是空的"，
> 是 3 条记录的小样本假象**——真实数据里错误经验能拿 0.71~0.80。

**⚠️ 但阈值只能管"多不像就不看"，管不了"长得像但其实不是一回事"。**
`cordon` 和 `pending` 修好之后仍然有 **0.60**——超过闸门。
真正救回来的是**排序**（正确那条匹配度更高），不是阈值。

而且在加节点层 token 之前，这两个签名**完全相同**，Jaccard = **1.00**，
阈值再高也没用。**所以真正的解法是让签名带上"能分辨处置"的 token，
不是调阈值。**

### 3. 只学"验证有效"的

```
applied      已批准执行，但还没回查  → 不参与检索（结论未知）
effective    回查确认症状消失        → 这才是可以教给下一次的经验
ineffective  回查发现症状还在        → 不许再教，并作废同症状同处置的旧案例
```

执行之后**重新算一遍症状签名**，症状消失了才算学到东西。
这条是整个记忆机制的核心——**大多数"Agent 记忆"存的是对话，这里存的是结果。**

### 4. 追加写的事件日志

同一个 `case_id` 可以有多条记录（`applied` → 后来追加 `effective`/`ineffective`），
**最后一条为准**。既保持追加写的简单，又能表达"这条经验被推翻了"。

---

## 为什么这么做（三个理由）

### ① 这个场景的症状是**可计算**的

K8s 的故障信号本来就是结构化的：`exitCode=137`、`restartCount=5`、
`Ready=False`、事件 reason 是 `FailedScheduling`。
**把它们降维成 embedding，是把确定的信号故意变模糊。**

### ② 决策要能被人审查

这个 Agent 的产出是一张**要人去点的审批卡片**。如果卡片上的依据是
"向量相似度 0.87"，操作员没法判断该不该点。

而结构化签名能给出：

> 匹配度 80% ｜ 当时改的是 api-gateway，这次是 order-service，参数要相应调整
> 症状：在跑但没就绪、部分后端未就绪、副本数不足
> 处置：rollout_undo({"namespace": "demo", "name": "api-gateway"})
> 结果：**回查确认症状消失**

**每一行都能追溯。** 这对一个安全敏感的工具是硬需求。

### ③ 零新依赖

运行时依赖只有 `kubernetes` 和 `requests`。没有向量库、没有 embedding 服务。
**"这个 Agent 到底能碰什么"可以被完整读一遍**——这是我在整个项目里一直守的取舍。

## 在这个项目里的优势（四条）

| 优势 | 具体体现在哪 |
|---|---|
| **可信** | 只教"验证有效"的；没验证过的、验证无效的都不进检索 |
| **可解释** | 能说清"为什么检索到它"——哪几个 token 重合了 |
| **可审计** | 检索结果进审计链；卡片上带着案例来源和匹配度 |
| **可推翻** | 回查发现无效 → 标记 `ineffective` 并作废同类的旧案例。**记忆会自我纠错** |

最后一条尤其少见：**大多数记忆机制只会累积，不会撤回。**

## ⚠️ 它的代价和真实局限（这段最值钱）

### 局限一：签名太粗会让**不同故障互相污染** —— 实测踩到

评测跑到第九轮，`cordon` 和 `pending` 两个场景**签名完全相同**：

```
cordon : ['pending', 'replicas_short', 'unhealthy']
pending: ['pending', 'replicas_short', 'unhealthy']
```

而它们的处置**完全相反**：一个要 `uncordon_node`，另一个**根本没有工具能解决**。

后果：给 cordon 写的经验会在 pending 场景以 **100% 匹配**命中，给出相反建议。

**修法**：给 `symptom_tokens()` 加节点层面的判定——
「有节点匹配但被 cordon 了」vs「一个匹配的节点都没有」：

```
cordon : ['node_cordoned',    'pending', 'replicas_short', 'unhealthy']
pending: ['no_matching_node', 'pending', 'replicas_short', 'unhealthy']
```

**这不是加个 token 就完事——它暴露的是：签名设计得"够不够分辨处置"。**
我是靠评测才发现签名有洞的，不是靠读代码。

### 局限二：冷启动 — 没修好过的故障永远学不到

案例库只吸收 `effective` 的修复。所以**从来没人修好的故障，记忆里永远是空的**。

这就是我后来加 **runbook** 的原因：人手写的"症状 → 处置"知识，
第一天就能用。但**渲染时必须和学习来的案例区分开**：

```
- 匹配度 100% ｜ **人工整理的处置经验**（⚠️ 未在本集群验证过，需自行判断是否适用）
```

**可信度不一样，就不能长得一样。**

### 局限三：Jaccard 阈值是个手工参数

0.5 是我拍的。实测下 cordon/pending 修好后仍有 0.6 的交叉匹配
（3 个 token 重合、各多 1 个）。**目前靠"正确的那条匹配度更高"来排序，
没有更硬的保证。**

## 和 RAG 的关系（这题一定会追问）

**不是"我不用 RAG"，是"这两件事不该用同一个工具"**：

| 问题 | 该用什么 | 为什么 |
|---|---|---|
| 「这个症状以前怎么修的」 | **结构化签名检索** | 症状可确定性计算；要能解释、能审计、能推翻 |
| 「K8s 官方文档 / SOP 里怎么说的」 | **向量 RAG** | 这是**真正模糊的文本**，正是 embedding 的主场 |

我文档里给 RAG 留的位置是后者：**把 K8s 文档和 runbook 做成可检索的知识库，
让 Agent 给处置建议前先查文档。** 那是 P1 的学习计划，不是我没意识到。

**面试时的说法**：
> 我不是排斥向量检索，是不把它用在能用确定性的地方。
> 症状匹配我用结构化签名，文档检索我会用 RAG——**两套并存，各管一头**。

## 一句话收尾（如果面试官只给你 20 秒）

> 我的记忆只学**验证有效**的修复，检索靠**确定性症状签名**而不是 embedding——
> 因为它的产出是一张要人签字的审批卡片，"为什么推荐这个"必须能讲清楚。
> 代价是签名设计得够细，我实测踩过坑：两个故障签名撞了，给出的建议完全相反。
