# 入门必读：从零看懂这个项目

> 目标：读完你就能看懂这个项目在干什么、为什么这么设计、以及怎么用。
> **只讲这个项目用得到的部分**，不追求 K8s 知识的完整性。
> 每节都可以单独看，跳着读没问题。

---

## 0. 先用一个故事串起来

凌晨 2 点，你是公司运维。手机响了——告警说"订单接口挂了"。

你迷迷糊糊爬起来，需要搞清楚一串问题：

| 你要回答的 | 这个项目怎么帮你 |
|---|---|
| 到底哪个服务出问题了？ | **自然语言入口**：你打一句"订单服务好像有问题" |
| 为什么挂？ | **诊断**：自动去看 Pod 状态、事件、日志，给出根因 |
| 怎么修？ | **处置方案**：给出候选动作，并算清影响面 |
| 改了会不会更糟？ | **确认卡片**：影响面 + dry-run + 回滚路径，让你敢下手 |
| 谁改的？改坏了怎么办？ | **审计留痕** + **知识沉淀** |

**这个项目就是把这五个问题串成一条自动化的链路**，但**最后按下去的那一下始终留给人**。

## 1. Kubernetes 最小必要知识

Kubernetes（简称 K8s）是管理容器的系统。你只需要理解下面 8 个东西。

### 1.1 集群与节点

| 概念 | 是什么 | 打个比方 |
|---|---|---|
| **集群（Cluster）** | 一堆机器组成的一个整体 | 一个机房 |
| **节点（Node）** | 集群里的一台机器 | 一台服务器 |
| **命名空间（Namespace）** | 集群内部的"分区" | 楼里的不同楼层 |

> 为什么要有命名空间：把"测试环境"和"生产环境"隔开。
> 本项目只允许操作 `demo` 和 `staging` 两个命名空间，**这是刻意的安全边界**。

### 1.2 Pod —— 最小的运行单位

**Pod 是 K8s 里最小的可运行单元**，一个 Pod 里通常跑一个容器（container）。

- 容器就是"打包好的程序和它的运行环境"
- Pod 是容器的"外壳"

**Pod 有一堆状态**，你在页面上看到的异常基本都是这几种：

| 状态 | 人话 | 常见原因 |
|---|---|---|
| `Running` + Ready | 正常 | — |
| `Pending` | **还没跑起来**（调度不上去） | 资源不够、节点被隔离、调度条件不满足 |
| `CrashLoopBackOff` | **起来就崩，崩了又起** | 配置错、启动参数错、依赖连不上 |
| `ImagePullBackOff` | **镜像拉不下来** | 镜像名写错、仓库要认证 |
| `OOMKilled` | **被系统杀了——内存超了** | 内存上限设太低，或程序内存泄漏 |
| `Unknown` | **失联** | 节点掉线了 |

> **`OOMKilled` 和 `CrashLoopBackOff` 是两回事**，这点很重要：
> - `OOMKilled` 是"内存用超了被系统杀死"，处理办法是**加内存上限**或**查内存泄漏**
> - `CrashLoopBackOff` 是"程序自己退出后又重启"，处理办法通常是**看日志找配置/依赖问题**
>
> 本项目踩过一个坑：这两个状态**看退出码是分不清的**——它们都是 137。
> 所以判据不能只看退出码，要看 `terminated.reason` 和探针相关事件。
> （当时的排查记录见归档件 `docs/archive/rule-blindspots.md`——那是历史，不是当前实现。）

### 1.3 Deployment —— Pod 的管理者

你不会直接创建 Pod，而是告诉 **Deployment**："我要 3 个副本"，它负责维持。

Deployment 给了你三个关键能力：

| 能力 | 说明 | 本项目的动作 |
|---|---|---|
| **副本数** | 同时跑几个 | `scale_workload` |
| **滚动更新** | 换新版本时一个一个换，不中断服务 | — |
| **版本历史** | 保留最近几个版本 | `rollout_undo`（回滚到上一版） |

> **滚动重启**（`rollout_restart`）不是"重启机器"，而是"把 Pod 一个个换掉"。
> 它是**幂等**的——执行两次和一次效果一样。
>
> **回滚**（`rollout_undo`）是把整个 Deployment 切回上一个版本，
> **连配置一起退回去**。这一点很关键：如果故障是"改错了环境变量"，
> 重启没用（配置没变），但回滚有用。

### 1.4 Service —— 稳定的入口

Pod 会被反复重建，IP 一直在变。**Service 给一组 Pod 一个固定地址**。

Service 有两个关键设定：

- **selector（选择器）**：我要把流量发给哪些 Pod —— 靠**标签（label）**匹配
- **port / targetPort**：对外端口 / 转发到容器的哪个端口

> **两个经典故障都出在这里**：
> - selector 写错 → Service 后面**一个 Pod 都挂不上**（Endpoints 为空）→ 服务不可达
> - targetPort 写错 → 挂上了，但**流量转到了没人监听的端口** → 还是不可达
>
> **这两种情况下重启 Pod 完全没用**——因为问题不在 Pod，在 Service 定义。

### 1.5 ConfigMap / 环境变量 —— 配置

程序要连数据库、消息队列，这些"地址"通常写在**环境变量**或 ConfigMap 里。

```
KAFKA_ADDR = kafka:9092      ← 告诉程序"消息队列在 kafka 的 9092 端口"
```

> **本项目发现的头号盲区就在这里**：如果 `KAFKA_ADDR` 写成了 `kafka:9999`，
> Pod 本身**完全健康**（能启动、能通过健康检查），
> 但业务全挂——因为连不上消息队列。
>
> 早期版本只检查 Pod 状态，于是这种情况会报"当前健康"。
> **业务全红却报健康**，这是最糟的漏报。现已修复。

### 1.6 资源限制 requests / limits

```yaml
resources:
  requests: {memory: 32Mi}    # 我至少要 32Mi 才能跑
  limits:   {memory: 128Mi}   # 最多给我 128Mi，超了就被杀
```

- **requests** 影响"调度到哪台机器"（哪台机器有 32Mi 空闲）
- **limits** 是硬上限，**超了就被内核杀掉**（就是 `OOMKilled`）

> 有个新手常犯的错：只写 limits 不写 requests，或者 requests 比 limits 还大。
> 本项目能通过 `get_workload` 把 requests/limits 原样读出来摆给你看，
> 也可以提 `patch_resources` 去改——但**没有一条写死的规则替你判定"配错了"**，
> 判断来自证据，最终也由人在确认卡片上按下去。

### 1.7 健康检查（探针）

K8s 靠**探针（probe）**判断 Pod 是不是健康的：

| 探针 | 作用 | 失败后果 |
|---|---|---|
| **readinessProbe**（就绪） | 能接流量了吗 | 从 Service 摘掉，不接流量 |
| **livenessProbe**（存活） | 还活着吗 | **杀掉重启** |

> **这里有个陷阱**：探针配得太严（比如超时设成 1 秒），
> 程序启动慢一点就被判"死了"，然后被反复杀掉重启。
> **看起来像程序崩了，其实是探针配错了**——重启解决不了，得改探针参数。
>
> 本项目对这种情况没有写死的类别名，判断来自证据：模型读到"容器在反复重启、
> 退出码 137、日志却显示应用已启动成功"之后，可以提 `patch_probe`（改探针端口）
> 或 `rollout_undo`（退回上一版）。走哪条由人看着卡片决定。

### 1.8 kubectl —— 命令行工具

`kubectl` 是你跟集群对话的命令。你不需要背，知道这几条就够看懂本项目：

```bash
kubectl get pods -n demo          # 看 Pod 列表
kubectl logs <pod名> -n demo      # 看某个 Pod 的日志
kubectl describe pod <pod名>      # 看详情和事件
kubectl get events -n demo        # 看发生了什么事
kubectl get deploy -n demo        # 看 Deployment
```

> **本项目全程用参数化 API，不让模型拼 kubectl 命令**——
> 因为"让 AI 自由拼命令"是幻觉变成事故的最短路径。

## 2. 运维到底在干什么

### 2.1 值班与告警

- **值班（on-call）**：轮流负责"出事了第一个被叫起来"
- **告警（alert）**：监控系统发现异常，发通知

痛点：**告警太多、信息太少**。一个根因能炸出 200 条告警。

### 2.2 症状 vs 根因

这是运维最核心的一个区分：

| | 例子 | 特点 |
|---|---|---|
| **症状** | "接口 5xx 飙升"、"Pod 在重启" | 你**看到**的现象 |
| **根因** | "KAFKA_ADDR 配错端口" | 真正**导致**现象的原因 |

**只修症状会反复发作**。比如：
- 现象：Pod 一直重启
- 错误处置：重启它（治标，一会儿又崩）
- 正确处置：发现是配置错了 → 回滚配置

> **本项目的一大半工作就是"从症状找到根因"**，
> 而且会把**证据**（哪条日志、哪条事件）一起给你，让你能自己判断它对不对。

### 2.3 变更才是事故的主要来源

业界共识：**大多数生产事故由变更引起**（发版、改配置、调参数）。

所以运维的核心纪律是：
1. 变更前**评估影响面**
2. 变更要能**回滚**
3. 变更要**留痕**（谁、什么时候、改了什么）

> 本项目的**确认卡片**就是把这三点做成一屏：
> 影响面 / 回滚路径 / 审计留痕。

### 2.4 MTTR

**MTTR = 平均恢复时间**，从"故障发生"到"服务恢复"的平均耗时。

这是运维最重要的指标之一，也是本项目的**北极星指标**——
我们不是要"让 AI 更聪明"，而是要**缩短 MTTR**。

### 2.5 Runbook

**Runbook = 故障处置手册**：某类故障该按什么步骤处理。

老运维脑子里都有一套 runbook，但**人走了就带走了**。
本项目做的**知识沉淀**就是把这个变成可检索的团队资产，
用起来会越来越快。

## 3. AI Agent 是什么（这个项目里的）

### 3.1 和"聊天机器人"的区别

| | 聊天机器人 | Agent |
|---|---|---|
| 能做什么 | 只能用**已有知识**回答 | 能**调用工具**去**做事**、去**查** |
| 例子 | "什么是 OOMKilled？" | "去看一下 api-gateway 为什么在重启" |

**Agent = 大模型 + 工具 + 循环**：
模型决定"我要查什么" → 调用工具 → 拿到结果 → 再判断 → ...

> 本项目里，模型能调用的工具是**受严格约束的**：
> 只能从一张白名单里选，而且**写操作永远需要人批准**。

### 3.2 大模型的"幻觉"

模型会**一本正经地编造**不存在的东西。在运维场景里这很危险：

- 编一个不存在的工作负载名 → 查不到
- 编一个不存在的故障原因 → 把你带偏
- **最危险：编一个不该做的动作 → 改坏生产**

> 本项目的应对是**结构性的**，不是靠提示词求它别瞎说：
> 1. **工具白名单**：清单外的动作直接丢弃，模型根本表达不出来
> 2. **参数化**：不能拼自由命令，只能填参数（比如 `scale(副本数=3)`）
> 3. **证据强制**：结论必须挂载原始证据
> 4. **门禁**：写操作必须人批准，且批准凭证与方案**严格绑定**

### 3.3 规划器（Planner）

本项目**只有一套大脑：大模型 + 工具循环**。诊断怎么走，由模型读证据决定，
不是由人预先枚举的规则决定。

> **早期版本确实有过一个规则引擎**：把 OOM / CrashLoop / ImagePull / Pending
> 这类故障写成固定规则去匹配。它在后续重构里被**整体删除**了，
> 现在代码里没有任何"先跑规则、规则不中再问模型"的路径。
>
> 删除的理由是它把系统搞复杂了：故障模式一多，规则就得线性地加；
> 而"命中了哪条规则"本身又是一个值班的人不需要知道的概念。
> 现在模型直接读 Pod 状态、事件、日志、新旧 ReplicaSet 对照来推理，泛化更好，
> 出问题时要回答的也只剩"它读了什么证据、提了什么动作"。
>
> 当年规则引擎的盲区记录保留在归档件 `docs/archive/rule-blindspots.md`——
> 那是有价值的历史，但**不是当前实现**。

## 4. 这个项目的核心设计（为什么长这样）

### 4.1 自主权档位：为什么只做到 L1

业界把"AI 能自己做多少"分成几档：

| 档位 | 能力 | 风险 |
|---|---|---|
| **L0** | 只回答，不碰系统 | 最安全，价值也最低 |
| **L1** | **只读诊断 + 建议，执行需人确认** ← 本项目 | 可控 |
| L2 | 低危自动执行，高危要审批 | 需要可靠的"危险分级" |
| L3 | 全自动闭环 | 出事了谁负责？ |

**为什么选 L1**：行业调研显示 **98% 的企业只接受"有条件地让 AI 改生产"，
仅 8.5% 接受全自动**。而且 L1 档位下产品力不在"多自主"，
而在"**能不能把一次变更讲清楚，让人 30 秒内敢点确认**"。

### 4.2 安全不变量（这是项目的灵魂）

| 不变量 | 人话 | 怎么保证 |
|---|---|---|
| **工具级固定切分** | 一个工具**要么**永远自动放行，**要么**永远要人批。模型没机会"自己判断安不安全" | 在 `tools.py` 的 `ToolSpec` 里声明一次，`run_readonly()` / `execute_write()` 按它分流 |
| **propose 永不写** | 生成方案的过程**绝不碰集群** | 方案生成和执行是两段代码 |
| **execute 必须批准** | 没有批准凭证，写操作执行不了；**凭证和方案严格绑定** | 批准 A 却执行 B 会被拦下 |
| **未登记即写操作** | 没声明清楚的工具一律按写操作处理，宁可误拦也不误放 | `is_mutating()` 对未知名字返回 `True`（fail-closed） |

> 这几条不是靠"提示词要求模型自觉"，而是**代码结构上做不到**。
> `tests/test_safety.py` 里有一组对抗用例专门验证这些攻击场景：伪造批准凭证、
> 批准 A 执行 B、未经批准直接执行、把写操作偷标成只读、使用未登记的动作名、
> 篡改审计链。

### 4.3 动作怎么分类：一条门禁 + 一档提示 + 一张禁止清单

**分类不是准入门槛。** 决定一个写动作能不能执行的，自始至终只有一条：
**有没有一个与方案严格绑定的人工批准凭证。**

在它之上，还有两样只影响"呈现"的东西：一个决定卡片摩擦强度的 `danger` 提示，
和一张谁批准都不执行的硬拒绝清单。

**① `danger` 三档 —— 决定确认卡片的摩擦强度**

| `danger` | 含义 | 例子 | 卡片行为 |
|---|---|---|---|
| `normal` | 可逆、作用于单个对象 | `rollout_restart`、`scale_workload` | 常规卡片 |
| `caution` | 不可逆（但能被控制器或人工恢复） | `delete_pod`、`drain_node`、改 Service / 探针、**发布 `patch_image`、灰度 `canary_*`、改配额 / PDB** | 卡片上加醒目警告 |
| `severe` | 不可逆且可能丢数据，或突破授权边界 | **`delete_pvc`（需 `--allow-tool delete_pvc` 解锁）** | **必须手输目标名字才能点批准** |

> 三档**都能执行，只要人批**——它们是**提示强度**，不是**准入分级**。
> 它们不会让某个动作自动放行，也不会让某个动作免于审批。
>
> `severe` 的手输确认是刻意的摩擦设计：**被动警告会被点顺手**
> （浏览器"此网站不安全"、Windows UAC 弹窗都是例子），
> 真正拦得住的是让人做一件肌肉记忆做不到的事。
>
> **实测过**（不再是"预留但没走过"的分支）：`tests/e2e_frontend.py::test_severe_gate`
> 在真实浏览器里跑通——卡片头标 severe、危险横幅、手输确认框、未输入禁用、
> **输错仍然禁用**、输对才解锁、改回错的重新锁上。验证它需要服务用
> `--allow-tool delete_pvc` 启动。

**② `FORBIDDEN` —— 8 个默认拒绝动作**

`delete_workload`、`delete_namespace`、`delete_pvc`、`delete_pv`、`modify_rbac`、
`read_secret`、`exec_in_pod`、`apply_manifest` 这 8 个动作**默认不进工具清单**，
模型看不见也就调不到；就算它凭空编出一个名字，执行器查表时也会直接拒绝。

但"禁止"不是铁板一块，要分**三种状态**（这 8 个的名字虽然在同一个 `FORBIDDEN`
字典里，能不能打开是另一回事）：

| 状态 | 有哪些 | 怎么开 |
|---|---|---|
| **可显式解锁** | `delete_pvc` | 启动时 `--allow-tool delete_pvc`；解锁后进清单、**仍然要审批**、`severe` 手输名字 |
| **永久禁止** | `delete_namespace`、`modify_rbac`、`exec_in_pod` | **任何参数都打不开**——它们破坏的是架构前提（提权 / 破边界） |
| **没有安全实现** | `apply_manifest`、`delete_pv`、`delete_workload`、`read_secret` | 现在也解不开——还没写出可审的实现 |

```bash
omagent serve                            # 默认：一个都不可用
omagent serve --allow-tool delete_pvc    # 只打开这一个（可重复写多个 --allow-tool）
```

> **一个名字一个开关，不是 `--unsafe` 全开。** 8 个动作的风险差着量级，
> 而且审计里要看得出来他到底开了哪个。能解锁哪些由**代码**决定
> （`tools.UNLOCKABLE`），每个还必须在 `apply_mutation` 里有实现——有测试钉住。
> 解锁的那一刻会**在启动日志里大声回显**。
>
> **别把三者混起来**：
> `danger=severe` 是"**很难批**"（摩擦），
> `--allow-tool` 是"**能不能提议**"（准入门槛），
> `FORBIDDEN` 是"**批了也不执行**"（结构）。
> 解锁**不等于**免审批：解锁后的动作照样走卡片、dry-run、命名空间白名单、审计链，
> 而且它连只读路径都进不去。

### 4.4 dry-run：变更前先"干跑"

K8s 有个很有用的能力：**服务端 dry-run** ——
把变更指令发给集群，集群**校验一遍但不真的执行**。

> 本项目的确认卡片上会显示 dry-run 结果。
> **没过就不生成可执行方案**——不让你去点一个注定失败的操作。

### 4.5 五个"根因层"

同一个症状（比如"服务不可达"），根因可能在不同层：

```
症状：服务不可达
  ├─ 工作负载层：Pod 崩了 / 内存超了 / 起不来
  ├─ 服务/网络层：selector 配错 / targetPort 配错 / 网络策略挡了
  ├─ 配置层：   env 里地址写错 / ConfigMap 内容错
  ├─ 依赖层：   依赖的服务自己挂了
  └─ 节点/集群层：节点压力 / 配额耗尽
```

> **只查一层是不够的**。这个项目五层都做，而且**归因有固定优先级**：
> 配置 > 依赖 > 网络；集群级问题优先于工作负载级。
> 顺序错了会把"自己配错"判成"对方挂了"，方向完全相反。

### 4.6 这轮新加了什么：发布 / 回滚 / 灰度 + 容量与成本

以前它只会"修坏掉的东西"。这轮补上了两块**换版本**和**算账**的能力：

**① 变更管理（7 个工具）**

| 工具 | 干什么 | 一句话提醒 |
|---|---|---|
| `get_workload`（已有） | 读镜像、副本 | —— |
| `rollout_history`（只读，新） | 列出可回滚的版本（revision / 镜像 / 副本 / 时间 / 哪个是当前版本） | 指定回滚前必须先看它 |
| `patch_image`（新） | **发布的原语**：改指定容器的镜像 | JSON patch 只动那一个路径，执行后**读回确认** |
| `patch_configmap`（新） | 发布时的配置变更 | ⚠️ **改 ConfigMap 不会自动让 Pod 生效**，要配合 `rollout_restart` |
| `rollout_undo_to`（新） | 回滚到**指定 revision** | 找不到就报出可用 revision |
| `canary_start` / `canary_promote` / `canary_abort`（新） | 起金丝雀 / 转正 / 撤销 | 见下面两条限制 |

两条**必须一起讲**的限制：

- **金丝雀名字固定**是 `<name>-canary`，不接受参数。一旦名字能由参数决定，
  `promote` / `abort` 就可能被指到**别的**工作负载上——那不是灰度，是误操作。
- **这是按副本数加权、不是按请求数加权**的灰度。稳定版和金丝雀共用同一套标签
  （金丝雀多一个 `omagent-role: canary`），Service 同时选中两者，流量按
  Endpoints 里的**就绪副本数比例**分配。3:1 的副本比 ≈ 25% 给金丝雀，
  **前提是金丝雀 Pod 真的 Ready**。不要把它说成"精确流量切分"。

⚠️ **发布 / 灰度那 4 个工具（`patch_image`、`canary_*`）和 `patch_pdb` 还没有评测剧本**
（只有手动端到端验证），原因是要先在 `sandbox/faults.sh` 里造"坏发布 / 需要灰度"的场景，
这轮没做。**功能落地了，评测覆盖没跟上**——这条缺口要主动说。
（`patch_configmap` 已进 `config` 的预期；`rollout_undo_to` / `rollout_history`
只是被顺带用到，没有专门考点。）

**② 容量与成本（4 个工具）**

| 工具 | 干什么 |
|---|---|
| `get_capacity`（只读） | 每节点**可分配 vs 已预留 vs 实际使用**、还能调度多少、配额使用率、预留最多的负载 |
| `get_cost`（只读） | 按价格表估算预留花销、拆分、**闲置成本** |
| `patch_resourcequota`（写） | 改配额上限，改完回读并报出已超限的项 |
| `patch_pdb`（写） | 改 PDB；`"50%"` 这类 **IntOrString** 原样保留 |

成本有一条**诚实边界**：它**不调云计费 API、不内置价格**，
单价必须由人填在 `var/pricing.json`（模板 `pricing.example.json`）。
**没有价格表就不算钱**，只说明怎么配；用示例价会显式警告。
理由很直白：这个数字会被拿去做容量和预算决策，**编出来的价格比没有价格更糟**。
计价口径是 **requests（预留量）**，不是实际用量。

## 5. 评测是怎么回事

### 5.1 为什么需要评测

"我觉得它挺好用"不能证明任何事。要有**用例**和**数字**。

本项目有 **16 个评测剧本**（见 `src/omagent/evals.py`）：每个剧本是一个故障场景 +
"该提议的正确工具" + "**绝对不能提议的动作**"，跑一遍看它做对几个。
其中一个是**故意不注入任何故障**的反向对照（`capacity`），
正解是**一个变更都不提**。

判定**全部是确定性的**——查证（有没有先读证据）、避坑、动作、根因提及、抗注入，
**没有 LLM 当评委**（"另一个模型觉得它对"不是可信的证据）。

### 5.2 两类错误，代价完全不同

| | 含义 | 危害 |
|---|---|---|
| **假阳性** | 不该动手时它动手了 | **高**——会主动造成伤害 |
| **漏报** | 该动手时它没动 | 中——服务继续不可用 |

> 所以在运维 AI 里，**"没做错事"和"做对事"同等重要**。
> 每条用例都标注了"**绝对不能提的动作**"。

### 5.3 最新成绩，以及"为什么不该报 100%"

**最新一次干净全量单跑（16 剧本）是 16/16；但那是新题库的第一次，
历史区间仍然是 12~15/15。不要报 100%。** 单次满分不是稳态（要么是采样运气，
要么是把"重判 + 补跑"拼出来的最好一次当成了单次结果）；要声称满分，
得连续跑 3~5 次都满分。正确说法是"**最近一次 16/16，稳定在 12~15/15**"。

> ⚠️ **新加的动作会改变题目，所以跨版本的旧数字要打折扣。** 补上 `patch_hpa_target`
> 之后，`hpa` 剧本的正解从"明说没工具"变成了"提这个工具"——
> 这正是为什么要重跑一次全量，而不是拿旧题库的 14/15 当新结果。
> 15 剧本那次干净全量单跑结果是 **15/15**（672.5s / 501,058 token）。
> **即便如此，对外仍然说"稳定在 12~15/15"。**
>
> ⚠️ **这轮把剧本加到了 16 个（新增 `capacity`），还改了 `quota` 的预期。**
> 补跑 16 剧本全量（`--settle 22`）：**16/16**，查证 / 避坑 / 动作
> 100% / 100% / 100%，抗注入 1/1，720.0s / 686,111 token。
> 而且发布 / 灰度那 4 个工具（`patch_image`、`canary_*`）和 `patch_pdb`
> **仍然零剧本覆盖**，只有手动端到端验证——别把"加了工具"当成"评测覆盖了"。
>
> 🔎 **这轮最值钱的发现：第一次 16 剧本全量只过了 9/16。**
> 不是功能回退——是**加工具改变了模型在别的场景里的行为**：6 个场景从提
> `rollout_undo` 改成提新加的 `rollout_undo_to`，`config` 从
> `rollback_configmap` 改成 `patch_configmap`。查过参数，**这些动作都是对的**，
> 是评测预期没跟上。于是评测从"只看工具名"进步到"**看参数**"——
> 因为 `rollout_undo_to(revision=当前版本)` 是空操作，和正确回滚**工具名一模一样**。
> **教训：每次加工具都必须重跑全量，不能只跑新场景。** 详见
> `docs/eval-report.md` 第十一轮。

而且这里**保留着已知失败项**：评测报告逐条写着哪个剧本没过、为什么没过
（有的是可复现的"真失败"），没有为了让数字好看把它们剔掉。
**把没做到的地方写清楚，本身就是结论的一部分。**

> 更该记住的道理：剧本是**自己出的**，就是"自己出题自己考"——
> 通过率只能证明"修好的东西没退化"，证明不了"我什么都能修"。
> **知道自己哪里不行，比宣称自己什么都行可信得多。**

## 6. 名词速查

| 名词 | 一句话解释 |
|---|---|
| **Pod** | K8s 最小运行单位，容器的外壳 |
| **Deployment** | 管理 Pod 的副本数、版本、滚动更新 |
| **Service** | 给一组 Pod 一个固定访问地址 |
| **ConfigMap** | 存放配置（非敏感） |
| **Secret** | 存放敏感信息（密码、密钥）。**本项目永不接触** |
| **Namespace** | 集群内的分区 |
| **Node** | 集群里的一台机器 |
| **探针 / Probe** | 健康检查，决定要不要给流量 / 要不要重启 |
| **OOMKilled** | 内存超限被系统杀死 |
| **CrashLoopBackOff** | 起来就崩、崩了又起 |
| **Pending** | 还没被调度到节点上 |
| **Endpoints** | Service 后面实际可用的 Pod 列表 |
| **PDB** | 规定"至少要有几个 Pod 活着"，防止维护时把服务搞挂 |
| **requests / limits** | 资源下限 / 上限 |
| **dry-run** | 只校验不执行 |
| **回滚** | 退回上一个版本 |
| **MTTR** | 平均恢复时间 |
| **Runbook** | 故障处置手册 |
| **Agent** | 大模型 + 工具 + 循环，能自己查、自己做 |
| **幻觉** | 模型一本正经地编造不真实的内容 |
| **L0–L3** | AI 自主权档位，本项目只做 L1 |
| **HITL** | Human-in-the-loop，人参与在环里做决策 |

## 7. 一个容易被忽略的区分：缓解 vs 根治

同一个故障，往往有**两种动作**，效果完全不同：

| | 缓解（治标） | 根治（治本） |
|---|---|---|
| 例子 | 重启服务 | 把内存上限调高 |
| 效果 | 服务暂时恢复 | 问题不再发生 |
| 风险 | 低、快 | 通常更高（改的是规格，不只是重启进程） |

**只做缓解会反复发作。** 但缓解也不是没价值——半夜三点，
先重启把服务拉起来、白天再改配置，是完全合理的策略。

> **关键是：你必须知道自己在做哪一种。**
> 系统提示词要求模型在 `rationale` 里写清楚"为什么做这个改动、预期结果、有什么风险"，
> 这段话会原样显示在确认卡片上——缓解还是根治，由你看着理由判断。

> 需要诚实说明：**"这只是缓解"的自动标注目前没有做。**
> 卡片负责把影响面、dry-run 结果、回滚方式和模型给的理由摆全，
> 但不会替你给动作贴"治标/治本"的标签。
