## 三种原型，别混着比

调研里最容易犯的错是把它们当同类：

1. **框架**（kagent）——给你积木，你自己造 agent。它不解决"怎么运维"。
2. **诊断工具**（k8sgpt）——只读，只解释"哪里不对"，不负责改。
3. **SRE agent / 平台**（HolmesGPT、Robusta、Botkube）——调查 + 处置闭环。

**你的项目属于第 3 类，最直接的对手是 HolmesGPT。** 其余两个 CNCF 项目
（k8sgpt、kagent）要么不做处置，要么不做具体场景。

## 最关键的一栏：审批模型

这是你的核心设计，也是我认为你该在面试里主打的点。各家做法分四种：

| 做法 | 代表 | 问题 |
|---|---|---|
| 无审批，靠 RBAC 收紧 | k8sgpt、Botkube、Robusta | 写动作一旦触发就执行；"人能手动发起"不等于"执行前要人批" |
| 有审批但**默认关闭** | kagent（`requireApproval` 要显式写）、containers/kubernetes-mcp-server（`confirmation_fallback` 默认 `allow`） | 默认不安全，漏配即失守 |
| 审批 + **任意命令逃生口** | HolmesGPT（`run_kubectl_command` 永远人工批）、kubectl-ai（kubectl + bash，默认询问） | 能力无限，安全性**完全押在"人会不会点错"上** |
| **能力枚举 + 结构化门禁** | **你的项目** | 灵活度低，但爆炸半径小得多 |

第三条和第四条的差别值得说清楚，因为这是你和 HolmesGPT 最本质的分歧：

- HolmesGPT：**能力不设限**（一个 catch-all 的 `run_kubectl_command` 什么都能干），
  用"永远人工审批"来兜。
- 你的项目：**能力先枚举**（15 个只读 + 10 个写，全是参数化 schema），
  再叠加 fail-closed 门禁 + dry-run 复跑 + 命名空间白名单 + 15 分钟 TTL + 哈希链审计。

也就是说：**HolmesGPT 把安全性押在"人"，你把安全性押在"结构"。**
两者都不是错的，但你的路线在"模型被说服"或"人点快了"的场景下更稳。
这一点在面试里是能讲出深度的。

### 实测修正：HolmesGPT 的 RBAC 比我原先写的宽得多

上一版我写的是「Helm chart 自动创建 scoped least-privilege ClusterRole」。
这轮拿到网络后直接读了它的模板
（`helm/holmes/templates/mcp-servers/kubernetes-remediation/rbac.yaml`），
**least-privilege 这个说法站不住**：

```yaml
kind: ClusterRole                    # 注意是 ClusterRole，不是命名空间级的 Role
  - resources: [deployments, statefulsets, daemonsets, replicasets]
    verbs: [get, list, patch, update, delete]
  - resources: [pods]          verbs: [get, list, watch, create, delete]
  - resources: [pods/exec]     verbs: [create]     # ← 任意 pod 内执行命令
  - resources: [pods/attach]   verbs: [create]
  - resources: [nodes]         verbs: [get, list, patch, update]  # ← 能改节点
  - resources: [jobs, cronjobs] verbs: [get, list, create, patch, update, delete]
```

**它确实不含 `secrets`**（这点我原来写对了），也确认不是 `cluster-admin`。
但它给了 **`pods/exec`、`pods/attach`、`nodes: patch/update`、以及工作负载的 `delete`**，
而且是集群范围。`pods/exec` 基本等价于「能进任何一个容器」——这不是最小权限，
是「最小到刚好能干活」。

这不是要否定 HolmesGPT 的设计，它的取舍很明确：**能力给足，用人工审批兜底。**
但把它说成 least-privilege 不准确，横向对比时不该这么写。

**反过来更衬出你的选择**：这个项目没有 `exec_in_pod`、没有 `apply_manifest`、
没有 `delete_*`——它们写在 `FORBIDDEN` 里，**根本不出现在模型可见的工具清单里**；
RBAC 也只需要目标命名空间里 deployments 的 `patch/update`。
同样是要「能干活」，你选的是**把能力砍到最小，而不是把审批加在最外面**。

## 你真正领先的地方

1. **提示注入防御——全场只有你做了。**
   我把 8 个项目的文档都过了一遍，**没有任何一个**提到"集群里读到的文本是不可信输入"、
   围栏化、或注入检测。而 HolmesGPT 的写工具是 `run_kubectl_command`、
   Flux159 有 `kubectl_generic` 透传——它们的日志/事件里如果被塞了指令，**没有任何一层专门防这个**。
   这是你最有辨识度的一个点，而且是真问题不是造出来的。

2. **"写操作唯一入口是审批卡"这件事，做到结构性可靠的只有你和 HolmesGPT。**
   其余要么没有，要么默认关闭。而且你是 fail-closed 的（未登记工具一律当写操作），
   k8sgpt 的自动修复是**默认开启的白名单**、containers 那个是**默认 allow**。

3. **记忆带"有效性回查"。**
   你的案例库只吸收**执行后复查确认症状消失**的修复。HolmesGPT 的 Skills 是
   "人 review 后 commit"，kagent/其余项目基本没有记忆。你这条自动闭环是独一份的。

4. **判据不用 LLM 当裁判。**
   HolmesGPT 和 containers 那个都用 LLM judge；你用确定性判据（可复算、免费、
   不会因为换了个裁判模型就变分）。代价是覆盖面窄。

## 定位建议

不要把自己说成"又一个 AI 运维助手"，那样会被拿去和 8.2k star 的 k8sgpt 直接比，
你会输。**建议的定位是"agent 的安全执行架构"**：

> 这个赛道 8 个项目里，写操作有强制人工审批的只有 2 个，做提示注入防御的是 0 个。
> 我从零实现了一套"能力枚举 + fail-closed 门禁 + dry-run 复跑 + 审计链 +
> 不可信输入围栏"的执行架构，并用 15 个真故障场景量化它的诊断质量。

三个可以主动展开的对比：

1. **"默认安全"和"默认能用"的分歧**——kagent 和 containers 那个都是默认不安全
   （审批要自己配、写默认开）。你选了 fail-closed：未登记的工具一律当写操作拒绝。
   这个取舍值得讲。
2. **"能力不设限 + 人兜底" vs "能力枚举 + 结构兜底"**——和 HolmesGPT 的分歧，
   见上面那一节。
3. **判据可复算 vs LLM 当裁判**——你的评测不依赖另一个模型的主观判断。
   但要**主动承认样本量小**，并说明你已经用重跑测了方差
   （`image`/`unhealthy` 是波动、`probe`/`pending` 是真失败）。这个诚实度本身是加分项。

## 落地成本对比

| 项目 | 用起来要多大代价 |

建议至少补一个 Docker Compose 或单命令启动的快速体验路径。
