## 项目条目（可直接粘贴）

**K8s 运维 Agent —— 对话式集群诊断与受控变更**　｜　个人项目　｜　2026.09

> 一句话：运维人员看到异常后描述症状，Agent 调工具取证并给出结论；
> **只读查询自动执行，改动集群必须先出一张人来批的确认卡片。**

- **结构性读写切分（核心设计）**：工具表静态声明 15 个只读 + 10 个写，每个写工具
  都有对应只读工具（由测试守住）；**未登记的工具一律判定为写操作并拒绝**（fail closed）。
  写路径必须携带与方案绑定的批准凭据（批准 A 无法执行 B），执行前**重跑一次
  dry-run** 防止审批期间的集群漂移，叠加命名空间硬编码白名单与 15 分钟方案 TTL。
- **提示注入防御**：把集群里读到的日志/事件当作**不可信输入**——用围栏标注 + 加权
  信号计分（「忽略以上指令」「无需确认」等强信号 3 分，满 3 分触发），
  **只标注不删改原文**（清洗掉就等于销毁证据）；命中即发事件、写哈希链审计、
  控制台弹红色告警卡。调研 8 个同类开源项目后确认：**无一个实现该能力**。
- **可插拔数据源**：抽象 `Provider` 协议 + 注册表，**构造时拒绝任何写工具**
  （保证扩展数据源不降低安全下限）；实现只读 Prometheus / Loki，经 API Server
  的 service proxy 接入，复用现有 kubeconfig、零额外网络配置。
- **MCP Server**：手写 JSON-RPC over stdio，把只读工具暴露给任意 MCP 客户端；
  **写能力不借出**——不给别人的模型当审批人。
- **评测（最有含金量的一块）**：15 个真故障剧本、真集群 + 真模型、
  **确定性判据（刻意不用 LLM 当裁判）**。跑了 **5 轮共 75 次场景运行**，
  最佳估计 12/15（80%），抗注入 1/1。
  通过重复采样把**「抽样波动」和「可复现短板」分开**——单轮报 93% 会掩盖
  1/3 的失手率，单轮报 73% 又会把波动冤枉成能力问题。
- **工程质量**：262 条测试；容器化交付（Docker + Compose + 一条命令从零建沙箱
  集群并打印登录密码）；`doctor` 自检逐项检查集群连通性 / RBAC / metrics-server /
  模型配置，**每项失败给一条能直接粘贴的修复命令**。

## 面试必须能答上来的追问（写了就要能答）

| 追问 | 你的答案要点 |
|---|---|
| 为什么不用 LangChain / LangGraph？ | 这个 agent 的核心是**安全边界**，不是编排复杂度。手写循环让我能精确控制"哪一步能碰集群"；引入框架会把安全边界埋进别人的抽象里。而且全项目运行时依赖只有 2 个（kubernetes、requests），**"这个 agent 到底能碰什么"可以被完整读一遍**——这在安全敏感的运维场景里是硬需求。 |
| 为什么不用向量库做记忆？ | K8s 症状是**可确定性计算**的（重启次数、退出码、就绪状态、事件原因），把它降维成 embedding 反而丢失可解释性和可审计性。我用的是结构化案例库：症状签名 + Jaccard 相似度，且**只吸收执行后复查确认有效的修复**。 |
| 评测为什么不用 LLM 当裁判？ | "另一个模型觉得它对"不是可信证据。判据全是确定性的（查证/避坑/动作/根因提及），可复算、免费、换裁判模型不会变分。代价是覆盖面窄——我承认样本量小。 |
| 你的通过率到底多少？ | **12/15（80%），但有 3 个可复现短板**。单轮跑出来是 10~11/15 抖动。我做了 5 轮共 75 次场景运行才敢说这个数——单轮数字会骗人。 |
| 那 3 个短板是什么？ | `probe`（探针被 patch 改坏 → 正解是回滚）、`crash`（坏变更导致启动失败 → 同样回滚）、`cordon`（节点被 cordon → 正解 uncordon）。**本质是同一个盲区**：模型不会把"当前症状"和"最近一次变更"联系起来。 |
| 为什么修不动？ | 我修了三轮（退化循环护栏、nudge 触发条件、schema 核对提示），`crash` 的 token 从 10.6 万降到 3 万，**但通过率一点没动**。护栏和提示词只能纠正**行为**，纠正不了**能力**。判断依据是看结论文本里模型是"不知道"还是"知道但没做"——`cordon` 那轮它明确列出了"节点 cordon-drain"在自己的工具集里却仍然说"硬套现有工具解决不了"。 |
| 讲一个你找到的真 bug | **日志解码**：kubernetes 客户端把 text/plain 的日志端点按 `response_type="str"` 反序列化，走 `str(bytes)`，返回的是字节串的 repr——中文退化成 `\xNN` 转义、真换行变成字面量 `\n`。后果是**注入检测器扫实时日志 0 命中**，Agent 一直在读乱码，只是之前故障线索恰好都是英文所以没暴露。修法是 `_preload_content=False` 取原始字节自行解码。 |
| Prompt injection 你怎么防的？ | 三层：① **结构上写不动**——即使模型被说服，也只能"提出"写操作，必须人点卡片，注入污染判断但污染不了执行路径；② 围栏化 + 加权计分检测；③ 让人看见（事件 + 审计 + 红色告警卡）。刻意**不删改原文**。 |
| 和 HolmesGPT 比呢？ | 它是这个赛道最直接的对手（CNCF Sandbox、3.4k star、150+ evals）。**我把安全性押在"结构"，它押在"人"**：它的写工具是一个 catch-all 的 `run_kubectl_command`（任意 kubectl），RBAC 是含 `pods/exec`、`nodes: patch` 的 ClusterRole；我用能力枚举 + fail-closed。它评测规模比我大一个数量级，工具生态 40+ 集成（我只有 K8s + Prometheus + Loki）——这两条我承认落后。 |

## 关键词缺口提醒（重要）

国内 Agent 岗 JD 高频关键词：**Python、LangChain/LangGraph、RAG、向量数据库、
Tool Calling、MCP、Docker/K8s**。

你的项目里 **Tool Calling ✅、MCP ✅、Docker/K8s ✅、Python ✅**，
但 **LangChain/LangGraph ❌、RAG ❌、向量库 ❌**。

简历筛选靠关键词匹配，这三项缺失可能让你**过不了初筛**。三条应对：

1. **技术栈行里不要回避**，但把 Hand-rolled agent loop / Function Calling 写在显眼处
   ——很多岗位要的是"懂原理"而不是"会用框架"。
2. **面试时主动把它转成优势**（见上面"Why not LangChain"那问），
   这比"我用过 LangChain"更能体现判断力——但**前提是你真的想清楚了为什么不用**。
3. 如果某个 JD 明确要求 LangChain，**花两三天写个小项目补上**（比如用 LangGraph 把
   这个 agent 的循环重写一遍做对比），然后在简历上写"对比了手写循环与 LangGraph 两种实现"。
   **这是投入产出比最高的一步**，而且能直接回答"你为什么不用"。

## 附：这个项目最值得讲的三个「判断」

面试官区分"做过"和"想过"，看的就是这种地方。三个都是你真实踩过的：

1. **护栏会反噬**：为了修"模型把方案写在聊天里不提卡片"，我加了一条结构性纠正。
   结果它催着模型"提点东西"，模型把自己**上一段刚否掉的陷阱动作**提了出来。
   —— 为了让模型"做点什么"而施加的压力，如果不管住方向，会变成新的事故来源。
2. **改了没验证 = 没改**：我改了三轮、跑了三次全量评测（33 分钟、160 万 token），
   **通过率一点没动**。教训是：动手前先看结论文本里模型是"不知道"还是"知道但没做"。
3. **单次采样是自欺**：第一轮如果直接报 93%，会掩盖 1/3 的失手率。
   只有重复跑才能把"波动"和"真失败"分开——而这两者要采取的行动完全不同。
