# 「都是人审批，为什么还要禁止」——这个论点对在哪、错在哪

> 这是一个我认为**最值得被挑战**的设计决定。下面是我用实测得出的结论，
> 不是立场。

## 你的论点（我认为大部分成立）

> 最终都要人审批，禁止只会让系统变窄。

**对的部分，而且是重要的部分：**

- 15 个评测剧本里有 **4 个**（`selector` / `port` / `probe` / `pending` / `hpa`）
  的正确行为是"**明说我没有工具**"——**不是它们不该修，是我的工具集修不了。**
- 这是**覆盖面被工具集而不是被安全哲学限制**，是真损失。
- `apply_manifest` 尤其突出：现实中大量处置就是改一段 YAML，
  参数化工具**根本表达不了**。禁掉它 = 放弃一大块真实工作。

## 但"都有人审批"这个前提有两个漏洞

### 漏洞一：dry-run 对删除**完全无效**（实测）

```
kubectl delete pod xxx --dry-run=server  → ✓ 通过
kubectl patch 非法值 --dry-run=server     → ✗ 拒绝
```

**dry-run 只验证"请求格式合法"，不验证"后果可接受"。**
删除请求永远合法——资源要么在要么不在。

这意味着：**对破坏性操作，我整套"干跑没过就不执行"的承诺是空的。**
只剩两道防线：人的那一次点击，和禁止清单。

### 漏洞二：审批疲劳是真的

如果工具集里同时有 `rollout_restart` 和 `delete_namespace`，
每天弹 20 张卡，人是**会点顺手的**。
而且这个项目自己的前提就是「**LLM 判断不可靠**」——
那为什么假定"人看着卡片一定可靠"？**同一个怀疑，得用在两边。**

## 所以正确的分法不是"全开"或"全禁"

**按 dry-run 管不管用、可不可逆来分：**

| 类别 | 例子 | dry-run 有效 | 可逆 | 建议 |
|---|---|---|---|---|
| 改配置 | `apply_manifest`、改 selector / 探针 / nodeSelector | ✅ | ✅ 能回滚 | **应该开** —— 覆盖面提升最大 |
| 可逆删除 | `delete_pod`、`delete_workload` | ❌ | ⚠️ 控制器会重建 | **可以开**，卡片标明 |
| 不可逆、不毁数据 | `drain_node`、`cordon_node` | ❌ | ⚠️ 要手工恢复 | 已有，保持要批 |
| **毁数据** | `delete_pvc`、`delete_pv`、`delete_namespace` | ❌ | ❌ **不可恢复** | 默认关，但**允许显式打开** |
| **提权 / 破边界** | `modify_rbac`、`exec_in_pod` | ❌ | ❌ **批准一次就等于绕过后续所有约束** | 建议永久不开放 |

**注意最后一行和其他行的性质不同**：`delete_pvc` 是"后果很重"，
而 `modify_rbac` 是"**批准它之后，命名空间白名单、审计、审批全都可以被绕过**"。
后者不是"危险动作"，是**边界突破**，它否掉的是整套架构的前提。

## 具体建议（不重建规则引擎）

你之前明确说过不想要规则那一套（"规则那一套给我整乱了"），所以**不搞分级引擎**。只做一件事：

**把 `FORBIDDEN` 从硬编码常量改成"默认清单 + 显式开关"。**

```bash
# 默认：现在的 8 个仍然全部禁止
omagent serve

# 要扩大覆盖面，显式打开你信任的那些
omagent serve --allow-tool apply_manifest --allow-tool delete_workload
```

打开之后：

1. 这些工具**进入模型可见的工具清单**（不是"调了再拒"）
2. 审批卡片上多一行：**「⚠️ 这个动作默认是禁止的，由你在启动时显式打开」**
3. 审计里记一条 `tools_unlocked`（谁、什么时候、开了哪些）
4. **每一条都必须能过 dry-run 才允许打开** —— 给不出的（`delete_*`、`modify_rbac`）
   启动时直接拒绝，理由和 provider 写工具那条契约一样：
   **提供不了无副作用预检的动作，不能纳入"干跑没过就不执行"这条承诺。**

## 我仍然建议永久不开放的

只有三个：**`modify_rbac`、`exec_in_pod`、`delete_namespace`**。

理由不是"危险"，是它们**破坏的是架构前提**而不是某个对象：

- `modify_rbac` —— 提权，之后白名单/审计/审批形同虚设
- `exec_in_pod` —— 任意命令，等于把"参数化工具"这个前提整个取消
- `delete_namespace` —— 一次性抹掉命名空间里**所有**东西，包括 PVC

其余全部可开。**这已经能补上 4 个评测场景里的全部正解。**

## 一句话

> 你说得对的地方：**禁止清单现在是按"感觉危险"列的，不是按"能不能兜住"列的**，
> 所以它确实过宽了。
> 我不同意的地方：**"有人审批"不等于可以不要禁止**——因为 dry-run 对破坏性
> 操作是空的（实测），而审批疲劳是真实的。
> 正确做法是**按"dry-run 管不管用 + 可不可逆"来决定开不开**，而不是全禁或全开。
