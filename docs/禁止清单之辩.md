# 「都是人审批，为什么还要禁止」——这个论点对在哪、错在哪

> 这是一个我认为**最值得被挑战**的设计决定。下面是我用实测得出的结论，
> 不是立场。
>
> ⚠️ **本文分两段读**：前面是**当时**的论证（保留原文，包括当时判断错的地方），
> 文末「后记」记的是**后来真的做出来的东西**——`--allow-tool` 落地之后，
> 哪些结论被实现了、哪些被证明定错了。**不要只看前半段就引用结论。**

## 你的论点（我认为大部分成立）

> 最终都要人审批，禁止只会让系统变窄。

**对的部分，而且是重要的部分：**

- 15 个评测剧本里，现在只剩 **1 个**（`hpa`）的正确行为是"**明说我没有工具**"——
  因为 `patch_hpa` 只能改 `minReplicas` / `maxReplicas`，**改不了 `scaleTargetRef`**。
  这一个确实是**覆盖面被工具集限制**（不是被安全哲学限制），是真损失。
  > **已更新**：`hpa` 这个也不成立了——后来补了 `patch_hpa_target`，
  > 评测里 `hpa` 的 `expect` 从 `∅` 改成了 `{patch_hpa_target}`。
  > 也就是说，**"15 个剧本里唯一一个正解=明说没工具的场景"这句话现在一个都不剩**，
  > 真正"只能明说"的只剩禁止清单里的动作（而且大多还没有安全实现）。
  > 这正是下面那条论点的胜利：**被工具集限制**的缺口应该用**加参数化工具**去补，
  > 不是靠放开 `apply_manifest`。
- **但要更正一条过时的说法**：`selector` / `port` / `probe` / `pending` 这 4 个
  以前也属于"只能明说没工具"，**那 4 个场景现在都有参数化写工具了**
  （`patch_service_selector` / `patch_service_port` / `patch_probe` /
  `patch_node_selector`）——所以它们**不再是"该不该放开禁止清单"的理由**。
  （`evals.py` 里这 4 个剧本的 `expect` 已经是这些工具；`pending` 还保留
  `allow_none`，退回"明说没工具"也不算错。）
- `apply_manifest` 仍然突出：现实中大量处置就是改一段 YAML，
  参数化工具**根本表达不了**。禁掉它 = 放弃一大块真实工作。
  （注意：补上面那 4 个工具走的是"**加参数化工具**"，**不是**放开 `apply_manifest`。）

## 但"都有人审批"这个前提有两个漏洞

### 漏洞一：dry-run 对删除**完全无效**（实测）

```
kubectl delete pod xxx --dry-run=server  → ✓ 通过
kubectl patch 非法值 --dry-run=server     → ✗ 拒绝
```

**dry-run 只验证"请求格式合法"，不验证"后果可接受"。**
删除请求永远合法——资源要么在要么不在。

这意味着：**对破坏性操作，我整套"干跑没过就不执行"的承诺是空的。**
只剩两道防线：人的那一次点击，和禁止清单。

### 漏洞二：审批疲劳是真的

如果工具集里同时有 `rollout_restart` 和 `delete_namespace`，
每天弹 20 张卡，人是**会点顺手的**。
而且这个项目自己的前提就是「**LLM 判断不可靠**」——
那为什么假定"人看着卡片一定可靠"？**同一个怀疑，得用在两边。**

## 所以正确的分法不是"全开"或"全禁"

**按 dry-run 管不管用、可不可逆来分：**

| 类别 | 例子 | dry-run 有效 | 可逆 | 建议 |
|---|---|---|---|---|
| 改配置 | `apply_manifest`（任意 YAML） | ✅ | ✅ 能回滚 | **仍值得讨论**；但 selector / 探针 / nodeSelector 这几种**已经用参数化工具开了**，不用碰禁止清单 |
| 可逆删除 | `delete_pod`、`delete_workload` | ❌ | ⚠️ 控制器会重建 | **可以开**，卡片标明 |
| 不可逆、不毁数据 | `drain_node`、`cordon_node` | ❌ | ⚠️ 要手工恢复 | 已有，保持要批 |
| **毁数据** | `delete_pvc`、`delete_pv`、`delete_namespace` | ❌ | ❌ **不可恢复** | 默认关，但**允许显式打开** |
| **提权 / 破边界** | `modify_rbac`、`exec_in_pod` | ❌ | ❌ **批准一次就等于绕过后续所有约束** | 建议永久不开放 |

> 这张表是**当时**的分法。落地之后的实际状态见后记，简单说：
> 「毁数据」这行只有 `delete_pvc` 真的做成了可解锁（`delete_pv` 还没实现）；
> `delete_namespace` 被移进了「永久不开放」那一档；`apply_manifest` / `read_secret`
> 仍是"没有安全实现、解不开"。

**注意最后一行和其他行的性质不同**：`delete_pvc` 是"后果很重"，
而 `modify_rbac` 是"**批准它之后，命名空间白名单、审计、审批全都可以被绕过**"。
后者不是"危险动作"，是**边界突破**，它否掉的是整套架构的前提。

## 具体建议（不重建规则引擎，当时写的）

你之前明确说过不想要规则那一套（"规则那一套给我整乱了"），所以**不搞分级引擎**。只做一件事：

**把 `FORBIDDEN` 从硬编码常量改成"默认清单 + 显式开关"。**

```bash
# 默认：现在的 8 个仍然全部禁止
omagent serve

# 要扩大覆盖面，显式打开你信任的那些
# ⚠️ 这两个只是**当时**举的例子——今天它们都还没有安全实现，这么写会直接报错退出。
#    真正落地的第一个可解锁动作是 delete_pvc，见后记。
omagent serve --allow-tool apply_manifest --allow-tool delete_workload
```

打开之后（这是当时设想的行为，其中**第 4 条后来被证明定错了**）：

1. 这些工具**进入模型可见的工具清单**（不是"调了再拒"）
2. 审批卡片上多一行：**「⚠️ 这个动作默认是禁止的，由你在启动时显式打开」**
3. 审计里记一条 `tools_unlocked`（谁、什么时候、开了哪些）
4. ~~**每一条都必须能过 dry-run 才允许打开** —— 给不出的（`delete_*`、`modify_rbac`）
   启动时直接拒绝，理由和 provider 写工具那条契约一样：
   **提供不了无副作用预检的动作，不能纳入"干跑没过就不执行"这条承诺。**~~
   ← **这条错了，见后记**：删除类动作的 dry-run **本来就不校验任何后果**（漏洞一
   自己就是证据）。按这条标准，`delete_pvc` 永远开不了；而它恰恰是运维最想要的
   那一个。把"dry-run 有效"当成解锁前提，等于用一把量不到东西的尺子做准入。

## 我仍然建议永久不开放的

只有三个：**`modify_rbac`、`exec_in_pod`、`delete_namespace`**。

理由不是"危险"，是它们**破坏的是架构前提**而不是某个对象：

- `modify_rbac` —— 提权，之后白名单/审计/审批形同虚设
- `exec_in_pod` —— 任意命令，等于把"参数化工具"这个前提整个取消
- `delete_namespace` —— 一次性抹掉命名空间里**所有**东西，包括 PVC

其余全部可开。**不过前面那 4 个场景已经用参数化写工具补上了正解；
现在只剩 `hpa` 那一个场景仍然只能明说没工具。**

> **上面这一段的两处已被后续实现更新**（保留原文是为了记录当时的判断）：
> ① `hpa` 后来有了 `patch_hpa_target`，不再"只能明说没工具"；
> ② "其余全部可开"没有照做——真正落地的只有**代码里明确登记、且已在
> `apply_mutation` 中有实现**的那一个（`delete_pvc`）。见后记。

## 一句话（当时）

> 你说得对的地方：**禁止清单现在是按"感觉危险"列的，不是按"能不能兜住"列的**，
> 所以它确实过宽了。
> 我不同意的地方：**"有人审批"不等于可以不要禁止**——因为 dry-run 对破坏性
> 操作是空的（实测），而审批疲劳是真实的。
> 正确做法是**按"dry-run 管不管用 + 可不可逆"来决定开不开**，而不是全禁或全开。

# 后记：`--allow-tool` 后来真的做了（2026-10-14）

上面这一整套建议里，**"默认清单 + 显式开关"这件事已经落地了**，但落地的形状
和当时的设想有出入。照实记下来。

## 做出来的是什么

```bash
omagent serve                        # 默认：8 个禁区动作一个都不可用，行为一个字没变
omagent serve --allow-tool delete_pvc  # 只打开这一个
```

代码里的分工（`src/omagent/tools.py`）：

| 常量 | 含义 |
|---|---|
| `FORBIDDEN` | **默认拒绝清单**（8 个）。用途是生成拒绝时的说明文字，所以必须全量、不随运行时变 |
| `LOCKED_WRITE` / `LOCKED_SPECS` | 默认锁着、但可解锁的动作定义（当前 1 个：`delete_pvc`，`danger="severe"`） |
| `UNLOCKABLE` | **能解锁哪些由代码决定**（当前只有 `delete_pvc`），不是一个配置项 |
| `PERMANENTLY_FORBIDDEN` | 任何参数都打不开的 3 个：`delete_namespace` / `modify_rbac` / `exec_in_pod` |
| `is_forbidden(name)` | **所有拦截点唯一该走的判断**（默认 fail closed），而不是直接查 `FORBIDDEN` |
| `forbidden_now()` | "现在**还**动不了什么"——已解锁的从这里消失。给界面和 `omagent tools` 用 |

`is_forbidden()` / `forbidden_now()` 跟 `FORBIDDEN` 分开是关键：如果不分开，
解锁之后会出现最尴尬的显示——同一个工具**同时**出现在工具清单和禁止清单里，
运维完全没法判断它到底能不能用。而拦截点若有一处仍直接查 `FORBIDDEN`，
就会留下"解锁了但还是被拦"的死角，且极难排查。

## 和当时设想不同的四件事（都是踩出来的）

**1. 落地的不是 `apply_manifest` / `delete_workload`，而是 `delete_pvc`。**
当时的例子随手写了那两个，实际第一个做的是 `delete_pvc`。原因很朴素：
它是最小、最具体、最容易验证的那一个，而 `apply_manifest` 是"任意 YAML"，
恰好是这个项目明确不要的口子。

**2. "必须能过 dry-run 才允许打开"这条门槛**（原文第 4 条）**被推翻了。**
删除类动作的服务端 dry-run **只校验请求格式，不校验任何后果**——
实测：删一个正在被 Pod 使用的 PVC，`kubectl delete pvc --dry-run=server`
**照样返回成功**。所以按那条标准，`delete_pvc` 永远开不了。
正确的做法是把安全边界放在别处（下一条）。

**3. `delete_pvc` 的安全边界**不在 dry-run，在这三处：
- **默认锁着**，必须启动时 `--allow-tool delete_pvc` 显式打开；
- **`danger="severe"`** → 前端要求**手输 PVC 名字**才能点批准
  （被动警告会脱敏，真正拦得住的是摩擦）；
- 走同一条**审批 + 审计**链，谁批的、什么时候批的都留痕。

**4. "一个名字一个开关"被坚持下来了，`--unsafe` 全开没做。**
理由当时就写了，现在更确定：8 个动作的风险差着量级，合并成一个开关等于
替运维做了"要么全信要么全不信"的决定；而审计里也再分不出他到底开了哪个。

## 那三个"永久不开放"按原样落地

`delete_namespace` / `modify_rbac` / `exec_in_pod` 现在是**独立常量**
`PERMANENTLY_FORBIDDEN`，`unlock_tool()` 遇到它们直接抛异常。
把"永久"和"还没实现"**分开表达**，是为了让"永久"这两个字有依据：
它们不是"做不到"，是"实现了也不该有这条路"。

其余 4 个（`apply_manifest` / `delete_pv` / `delete_workload` / `read_secret`）
仍在 `FORBIDDEN` 里、**还不能解锁**——因为没有安全实现。这一点在
`unlock_tool()` 的报错里写明了（"其余 N 个还没有安全实现"），
测试也钉着：`UNLOCKABLE` 里的每个名字都必须在 `apply_mutation` 有实现，
否则解锁出来的是个"看得见、一提就报未实现"的空壳。

## 一句追加的话

> **"禁止清单过宽"这个批评，最后不是靠删掉禁止清单解决的，
> 而是靠"默认锁着 + 一个名字一个开关 + 解锁后仍然要人批"解决的。**
> 也就是说：**同意你"系统不该因此变窄"的目标，但没同意"所以取消禁止"这个手段。**
> 而 dry-run 那条准入门槛被我自己推翻了——**用一把量不到东西的尺子做准入，
> 比不做准入更糟**，因为它会给人"我验过了"的错觉。
